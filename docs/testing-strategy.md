# CoworkOS CLI 和 App 测试体系

按五个递进环节组织：**基础功能 → CLI 专门功能 → App 功能 → App 内应用功能 → 具体用户 case**。先确认核心机制正确，再确认用户入口正确，再确认应用能力正确，最后确认组合起来能完成真实任务。

完整清单见 [五个环节的用例目录](testing-case-catalog.md)。目前是设计与待落地清单，现有测试需逐项核对覆盖。本套体系在每次发版前本地运行，不新增 GitHub CI 或 PR 门禁。单元、集成、E2E、真实模型和风险等级是每项测试的执行属性，详细规则见 [本地执行与发布规则](testing-execution-guide.md)。

当前提供 [本地执行入口](testing-local-run.md)。`npm run test:release` 运行现有确定性 suite，按五个环节保存本地报告；具体覆盖待核对、人工/原生条件不足与新权限体验目标分别列出。独立应用实例、消息队列与多模型协议已进入目录。

| 环节              | 测试范围                                     | 通过后能够确认                |
| ----------------- | -------------------------------------------- | ----------------------------- |
| 一 基础功能       | CLI 和 App 共用的 harness 核心               | 每个底层功能及协作机制正确    |
| 二 CLI 专门功能   | 终端入口、命令、配置、安装、交互             | 用户经 CLI 能正确使用核心能力 |
| 三 App 功能       | 桌面宿主、聊天、输入、导航、设置、退出和升级 | 用户经 App 能正确使用核心能力 |
| 四 App 内应用功能 | 工作台、文档、外部软件操作                   | 用户与 Agent 能在应用中协作   |
| 五 用户 case      | 从用户目标到完整交付                         | 多个功能组合后仍然正确        |

CLI 的执行路线是“一 → 二 → 五”；App 的执行路线是“一 → 三 → 四 → 五”。App 普通聊天任务可以直接从第三环节进入第五环节。五个环节是审阅和维护顺序，两个入口不互为发布前置条件。

## 一 基础功能测试

测试 CLI 和 App 共用的核心，通过函数、服务接口和真实运行进程执行。此环节重点判断机制是否正确，终端交互和 App 界面分别在后续环节验证。

| 功能组            | 主要检查内容                                                 |
| ----------------- | ------------------------------------------------------------ |
| 文件与命令工具    | 创建、读取、修改；cwd、stdout/stderr、退出码、超时、保护路径 |
| 模型与工具调用    | 配置及参数、流式响应、工具参数和结果、错误分类、重试及取消   |
| Task 和 Run       | 创建、状态转换、完成条件、并发启动、停止、失败和恢复         |
| 单 Agent 与上下文 | 多轮对话、补充指令、memory、压缩、checkpoint、原会话继续     |
| 多 Agent 协作     | 同步/异步委派、状态查询、消息、取消、回调、结果汇总          |
| 队列和持久化      | 租约、优先级、去重、原子写、崩溃恢复、损坏数据               |
| 人工问答          | 提问、等待、回答、重复提交、问题归属和恢复                   |
| 长程能力          | jobs、休眠/唤醒、Watch、Virtual Agent、实验记录、预算        |
| 输入与交付        | 附件解析、图像输入、Skill 路径、产出物发布、下载字节         |
| 安全和可靠性      | 权限拒绝、凭据脱敏、磁盘故障、进程回收、性能与泄漏           |

每个功能先测正常行为，再补适用的失败、取消、重启恢复、重复或并发行为。校验与状态转换用单元测试；跨服务行为用集成测试；运行生命周期必须包含真实子进程。模型可以使用本地协议服务控制输出，文件和工具执行使用生产实现。

**验收要求：**核心结果与落盘状态一致；不会误报完成、丢失已提交数据或越权；取消与恢复行为可以独立核对。例：工具写入成功后模型断流，已提交内容仍在，Task 正确失败，继续时能够核对已有结果。

### 人类参与的执行协议

基础层单列 `INTERACT-01` 至 `INTERACT-08`：正常多轮、运行中补充、连续修正、显式停止、完成/取消竞态、人工问题与普通输入、更新目标、后台事件并发。分别核对输入接收、持久化、进入模型上下文及结果，不能把“消息已接受”等同于“要求已生效”。

`INTERACT-09` 至 `INTERACT-14` 进一步检查：同 Task 的旧 Run 请求、工具结果与补充输入同时保留、保存失败与消费恢复、多进程恢复冲突、被拒输入零污染，以及查看仍在运行任务与修复崩溃残留状态的区别。

插入指令在约定执行边界影响后续行为；显式 Stop 走取消链路。正在运行的工具是否可取消由其契约决定，已发生副作用不会因补充要求自动撤回。

## 二 CLI 专门功能测试

基础功能通过后，使用安装后的 atria 验证终端用户体验。

| 功能组         | 主要检查内容                                                     |
| -------------- | ---------------------------------------------------------------- |
| 安装与命令入口 | tgz 安装、独立 prefix、version/help、无源码与开发依赖            |
| 初始化与配置   | init、隐藏密钥输入、配置权限、覆盖顺序、已有配置保护             |
| 项目与路径     | 普通业务 config.json、外部项目、空格/Unicode 路径、cwd           |
| 命令与参数     | task/worker/human/watch 等实际公开命令、缺参数、非法参数、退出码 |
| 终端交互       | TTY/pipe、stdin/EOF、Ctrl-C/SIGTERM、运行中输入、终端状态恢复    |
| 会话与诊断     | --continue、历史选择、原 Task 身份、日志位置、--no-session 说明  |
| 检查与升级     | doctor、真实连接探测、依赖缺失、前版升级、重装和数据保留         |

基础执行规则在第一环节定义；这一环节检查它们经过命令、参数和终端操作之后仍然正确。例如：基础层验证取消能回收进程，CLI 层验证用户按 Ctrl-C 会取消正确 Task 并恢复终端。

**验收要求：**从独立安装包按用户文档完成首次配置、启动、停止和继续；不依赖仓库 dist；不改普通业务配置；继续到原会话和 Task。优先核对 `CLI-03` 配置碰撞与 `CLI-04` 恢复身份。

### 运行中交互和终端多轮显示

CLI 单列 `CLIHUMAN-01` 至 `CLIHUMAN-05`：流式输出时输入/发送、多轮显示、取消后改要求、Unicode/多行粘贴、人工问题和回调。PTY 中核对输入不被输出覆盖、消息归属、取消状态及原会话恢复；终端键位沿用实际帮助，不编造未提供的控制。

`CLIHUMAN-06` 至 `CLIHUMAN-11` 把终端边界细化为粘贴末尾换行、中文/Emoji 编辑、弹窗键位优先级、历史迟到读取、断连/取消后输入恢复和实时缩放。需要核对真实提交内容和操作数量，不能只看终端截图。

## 三 App 功能测试

测试 App 自身的桌面与交互能力。即使没有打开 TXT，也应能独立验证这一环节。

| 功能组         | 主要检查内容                                              |
| -------------- | --------------------------------------------------------- |
| 安装与启动     | 最终 DMG/App、首次打开、包内后端、Finder 启动、随机端口   |
| 会话管理       | 新建、重命名、置顶、归档、搜索、历史导航和持久恢复        |
| 输入与发送     | 多行、附件、语音、草稿、发送/停止、晚返回、切换会话       |
| 运行与消息显示 | 文本/思考/工具流、失败状态、重试、耗时、重连、阅读位置    |
| 模型设置       | 首次配置、测试/保存连接、高级参数、加密密钥、忙碌修改保护 |
| 窗口和交互     | 窄窗口、分栏、全屏、菜单、键盘、焦点、减少动画            |
| 桌面边界       | preload/IPC、可信主窗口、外链/预览、正式/Dev/CLI 数据隔离 |
| 退出与更新     | 草稿保存、保存失败保留窗口、后端收尾、重启、迁移、升级    |

renderer 交互可先用 Chromium 自动测试；原生窗口、IPC、加密、退出和最终包必须在真实 Mac App 验证。用户操作应从可见控件触发，核对对应 Task 的真实事件和文件。

**验收要求：**消息、草稿、附件和晚返回始终属于正确会话；用户可启动、停止和恢复任务；失败有正确提示；退出重启不丢输入。例：发送 A 后切到 B，A 的迟到回包不能清空 B 的草稿或抢回导航。

### 运行中人类交互与多轮显示

App 单列两组必跑功能：

| 功能组               | 必须覆盖                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------- |
| 运行中交互 APPHUMAN  | 正在生成/执行工具时补充；修改要求；显式 Stop；停止后继续；连续输入；人工问答；完成边界的 409 回退；切会话和重启 |
| 多轮正常显示 APPCHAT | 至少 5 个正常回合；每轮文本/思考/工具/时间归属；插入消息顺序；合法相同内容；历史阅读；跨轮 Markdown；刷新和重启 |

正常多轮是基线，另加“正常 → 打断 → 继续 → 失败 → 恢复”的混合轨迹。每次都同时核对真实执行事件和可见界面，防止执行正确但显示串轮，或显示已接收但指令从未生效。

确定性回归应覆盖 `APPHUMAN-09` 至 `APPHUMAN-14`、`APPCHAT-09` 至 `APPCHAT-11` 和 `DESKTOP-06/07`：旧 Run 操作、消息身份合并、IME 与弹窗、附件准备失败、问题/授权失效、执行中历史重建、200 轮历史、内部消息来源，以及客户端断连和宿主退出的不同契约。HTTP 响应、实时事件和历史快照需分别打乱时序验证。

## 四 App 内应用功能测试

先测试应用共用流程，再测试各应用的领域功能。共享资源契约可无界面测试；应用工作台中的人工操作必须经过真实 UI。

| 功能组       | 主要检查内容                                               |
| ------------ | ---------------------------------------------------------- |
| 通用工作台   | 发现、打开、新建、绑定、文件切换、空窗口转资源、跨对话引用 |
| 编辑与保存   | 人工/Agent 协作、草稿、版本 CAS、外部修改、冲突、候选接纳  |
| 历史与交付   | 比较、撤销、导入/导出、重启恢复；预览/导出不修改源资源     |
| TXT          | 新建、选区修改、重命名、清空、保存、撤销、下载、多轮协作   |
| 外部应用操作 | 单窗口授权、观察、输入、效果核验、权限到期、暂停和人工接管 |
| 扩展接口     | Adapter/MCP 注册、工具发现、版本合同、取消和宿主生命周期   |

新增应用先复用“打开 → 创建 → 绑定 → 编辑 → 保存 → 冲突 → 历史 → 导出 → 恢复”的共用测试，再增加自身领域验收。缺依赖、权限不足、编译/脚本错误、预览迟到等变体归在对应应用下。

软件测试逐步操作见 [应用本地验收手册](testing-application-release.md)：使用固定 TXT与原生输入窗口，记录用户操作、可见反馈、实际文件和体验问题。首次安装、空状态、参数编辑、保存/导出、错误修复和人工协作均有独立检查步骤。

**验收要求：**人工与 Agent 操作同一正确资源，冲突不丢草稿，领域结果可以独立验证。GUI 核对目标控件和保存文件，不能只看“事件已发送”。

用户友好作为通过标准的一部分：正常操作不要求用户理解 revision/CAS、编写脚本或反复授权；错误说明用户接下来怎么做；重试不清空输入。Computer Use 的权限改进目标是任务内一次授权连续使用、更长有效期，以及用户主动选择的同应用窗口范围。当前固定 5 分钟、单窗口仍按现行行为回归，宽松模式单列为待实现体验目标。

CLI 若提供无界面应用工具，应复用领域契约并验证该入口；不要求 CLI 提供 App 工作台或原生窗口授权。

### 人机同时操作应用

在对应应用下补 `COLLAB-01` 至 `COLLAB-03`：用户修改资源后 Agent 继续、计算中停止并换参数、浏览文件与实际绑定目标不同。除对话正确，还要检查资源 revision、人工修改、取消后的派生结果及实际编辑目标。

`COLLAB-04` 检查计算期间重开工作台后的作业状态、结果归属和资源恢复，不因重连再启动一次计算。

## 五 具体用户 case 测试

从用户提出一个目标开始，到 Agent 执行、交互、恢复和最终交付结束。前四环节确认局部行为，此环节确认组合后的完整结果。

| 任务类型 | 代表 case                      | 最终独立验收                            |
| -------- | ------------------------------ | --------------------------------------- |
| 文件任务 | 创建中文文件、读回并交付       | 内容、路径和下载字节正确                |
| 代码任务 | 修 bug、运行测试、交付代码     | 隐藏测试通过，原测试未改                |
| 数据任务 | CSV 统计、缺失值处理、报告     | 数值与结构由独立程序核对                |
| 多 Agent | 两个子任务并行后汇总           | 实际委派、正确消费、结果准确            |
| 人工交互 | 询问后等待，用户回答再继续     | 按正确回答执行，不替用户作答            |
| 中断恢复 | 取消/断流后退出，再继续        | 原 Task、已知副作用不重复、最终结果正确 |
| 交付任务 | 外部文件发布并下载             | 源文件、索引、路径和 hash 一致          |
| 应用协作 | TXT 多轮；GUI 输入保存         | 真文件、几何、工程或控件符合任务        |
| 文档产出 | PDF/DOCX                       | 内容正确、可打开、渲染可读              |
| 长程任务 | Watch 唤醒、压缩继续、迭代优化 | 事件/上下文完整，指标真实，预算有界     |

用例 ID 保留稳定标识，已移除能力的用例从清单删除。前 8 个基础任务及 `CASE-17` 至 `CASE-21` 五个交互任务在 CLI/App 分别执行；应用和原生任务按入口及依赖配置执行。`CASE-22` 至 `CASE-24` 优先用于两端确定性时序回归；`CASE-26` 验证独立应用流程，按应用批次记录，暂不扩大核心真实模型发布批次。

同一 case 可以有确定性协议模型与真实模型两种变体。前者用于稳定回归，后者允许模型自由规划并检验真实能力；两者使用相同的独立产物验收标准，结果分别记录。Agent 回复“完成”不能作为唯一通过标准。

### 人类持续参与的任务

新增五个完整 case：5 轮逐步完善报告、执行中插入限制和输出格式、停止后改变目标、人工问答期间补资料与子任务回调、多轮混合取消/失败后恢复并重启查看。每个任务同时检查**输入实际生效、最终产物正确、对话正常显示**，不能只测接口返回或最后一条回复。

### 新功能和更新如何接入

1. 判断新功能属于前四环节中的哪一个，在对应功能组增加正常与适用的异常测试。
2. 共享核心变化补 CLI/App 的相关入口测试；应用变化补工作台及领域验收。
3. 新增用户可完成的目标时，再增加第五环节完整 case，关联其所依赖的功能测试。
4. Bug 修复先保存最小失败复现，再验证相同标准通过，保留为后续回归。
5. 使用 [用例模板](testing-case-template.json) 记录步骤、通过标准、依赖、实现位置和执行频率。

review 也按这五个环节逐段进行：确认功能是否齐全、行为是否符合产品预期、通过标准能否独立判断。每项填写“已完整覆盖、部分覆盖、待实现、不适用”以及对应测试，避免把规划清单当作已完成成绩。

### 执行与发布

每次发版前在本地按这五个环节执行，补齐支持平台、最终安装包及核心真实用户 case。当前 suite、实际软件操作、人工权限验收分别记录；必跑项跳过记为未完成，重跑保留首跑记录，发布证据绑定最终包 hash。开发时可按需复现，不要求按 PR 或定时自动触发。

细节统一放在 [执行与发布规则](testing-execution-guide.md)，保持这五个功能环节作为唯一主目录。
