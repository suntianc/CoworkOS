# 长期目标架构与边界

## 用户看到的是什么

P4.5 已移除长期任务的界面入口，后端能力与接口保留；本节记录移除前的交互组织。原侧栏有「长期任务」入口及有内容时出现的未读提示。目标总览、全局动态分别组织；点进目标后，进展、计划、设置与完整动态按需查看。待决策优先，暂停目标收起，日志与来源配置留在高级设置。创建首先描述想达到的效果，名称可自动产生。普通记录不占用聊天页面；默认仅提醒重要结果，全部更新策略可逐条提醒普通内容，选择周报时则定期合成一条应用内动态。具体交互见 [长期任务交互组织](long-term-goals-ux.md)。

可以从入口创建，也可以在聊天里交代持续责任。模型使用 `manage_goal` 显式登记，再使用 `create_watcher(programId=...)` 关联来源。后台目标有自己的 Task；会话内目标使用已有 Task。一个目标可以有多个来源，来源不会再分别创建后台聊天。

暂停保留计划、通知与已接受的事件；恢复排入明确的恢复指令。结束目标后不再采样或复盘。独立后台 Main 正在生成时，暂停/用户结束会通过 Pi 的 `abort()` 终止当前生成；会话内暂停只限制该目标的工作，不中断同一聊天里的其他工作。

## 数据与责任边界

- `WatchProgram.goal`：目标简报、偏好、完成标准、计划、事实、进展、等待条件、下次复盘及汇总时间。沿用一个归属对象，不引入第二份任务注册表。
- `GoalStore`：目标锁、版本校验和持久化。目标版本独立于来源成员变更；模型用旧版本提交时返回冲突，不能覆盖用户修改。
- `GoalManagement`：创建、修改、进展、报告、控制与回答的共用业务规则。Pi 工具和 Dashboard 都调用它。
- `goal-delegation`：在模型注册/交接请求所属的 Run 中原子保存目标归属。该 Run 不能再创建替代采集器，省略 `programId` 或改用自定义包也不能绕过；目标自己的 Main 正常登记来源。收据跨进程恢复，不限制另一个用户 Run 或显式 HTTP 来源操作。
- `GoalSupervisor`：修复持久化副作用、将用户指令/到期复盘写入 Inbox、按时生成普通内容汇总。它不负责推理或制定计划。
- `WatchSupervisor`：确定性采样与来源重试。分析和采样分开运行，慢模型不阻塞采样。
- `GoalActivityStore`：主题记录、证据、通知、汇总收据和已读状态。在同一个原子快照里写报告、去重收据与通知。
- `goal-decisions`：先持久化决策意图，再幂等生成 HumanRequest 与提醒。中断后 Supervisor 修复；不会为同一决策反复创建问题。
- `goal-context`：启动/恢复和上下文压缩时提供最多约 16,000 字符的工作状态；历史资讯和通知正文不自动注入。
- `goal-service` / `goal-routes`：工作区定位及 HTTP 映射；前端控制器只呈现状态和提交用户操作。

## 一次完整执行

1. 用户创建“关注 Claude Code 官方发布，重要变化及时告诉我，普通内容周报”。保存目标并登记待规划指令。
2. Supervisor 将指令幂等写入现有 Main Inbox。Main 启动后读取当前目标及版本。
3. Main 登记计划，为发布与公告关联来源，探针验收通过后才启用。首次建立现有内容的基线。
4. Main 用 `record_goal_progress` 保存实际进展，登记活动来源或明确的下次复盘时间，然后停泊。
5. 来源按频率运行脚本。无变化时不运行模型；候选事件经过阈值/关键词等规则后，才按事件模式决定直接唤醒 Main 或先做语义判断。
6. Main 核实事件，用稳定的 `topicKey` 调用 `publish_goal_update`。同一具体事实从多个来源出现时合并证据；同一优先级不重复提醒；优先级提升允许提醒。
7. 普通内容只记记录或进入周报；重要变化与决策产生持久的应用内动态。周报由已接受的普通记录确定性拼合，无需再次调用模型。
8. Main 保存新计划与等待条件。用户回答问题后，答案走 HumanRequest → Inbox 的持久链路继续处理。一个目标的问题不阻塞同一会话的其他目标。

持续目标既无活动来源、也无明确复盘时间时，进展工具拒绝登记无效等待；Main 忘记登记进展或最后一个来源失效时，状态变为「需要检查」并保留一条提醒，不靠无限模型重试来掩盖卡住。

## 成本与运行边界

省的是空闲模型调用与重复上下文，不是限制每次 Main 的能力。Main 和监控分析共用主体的模型、轮次和 token 配置。采样间隔、每日候选分析/唤醒次数控制触发频率；没有单独的监控 token 预算。

采集时钟与模型复盘时钟分开：`cadenceSeconds` 只驱动探针；目标复盘通过 `record_goal_progress(nextReviewAt)` 交给 GoalSupervisor。会话内目标用 `sleep_until(programId=...)` 明确停泊归属，不另建 Task 轮询时钟。独立后台目标的旧 `main.scheduled_wake` 及明确带目标身份的轮询被消费且不唤醒模型；共享会话不能仅凭监控列表推断时钟归属，未带目标身份的旧时钟和独立定时请求继续投递。非目标任务和目标显式复盘照常运行。

这是本机持久服务：关闭浏览器不影响正在运行的后台服务；机器休眠、退出服务或调度禁用时不会继续观察，启动后恢复持久状态。此版本通知为应用内动态与未读数，不承诺系统级推送。跨来源去重依赖 Main 为同一具体事实复用主题键；不同语义键不自动视为同一新闻。周报使用已核实记录，不会替代一次主动全网研究。

## 接口、兼容与验证入口

HTTP 字段、分页和冲突状态以 [Product API](product-api.md#long-term-goals) 为主；用户入口和宿主生命周期见 [运行时参考](runtime-reference.md#长期目标接口与调度)。模型通过 `manage_goal` 查询/创建/修改目标、通过 `record_goal_progress` 保存进展、通过 `publish_goal_update` 汇报。跨会话交接用 `manage_goal(action=steer)` 持久投递要求；排队成功不表示工作完成，交接不改变简报、不恢复暂停目标。

注册会话创建后台目标或尝试向另一个 Main 交接时，Run 保存 owner Task/目标身份及当前用户请求身份的归属收据。同一请求的后续模型轮次、重试与重启继续受限；即使目标暂停导致交接被拒绝，也不能回退成独立监控。同一 CLI Run 或等待中的共享会话接受新的用户消息后，新请求可以独立登记来源。身份来自已持久化且已交给模型的真实用户消息，不随模型调用、Inbox 监控事件或内部续执行改变；精确重放沿用请求快照中的身份，旧快照无法确认身份时保守保留 Run 限制。收据不是交付或完成证明；实际交付状态仍由目标 Inbox 表示。旧收据保留并关联升级前的请求，新消息不会删除历史收据。

`manage_goal` 使用 Pi 的顺序工具执行模式，同一响应中的后续采集器调用必须等归属落盘后再检查，不能与创建/交接并发穿透。

暂停是持久意图，不能因来源错误、旧时钟或相似请求而自行恢复。旧记录中来源全暂停也按暂停处理；只有用户显式恢复才释放保留工作。背景目标不能通过新建目标/来源规避暂停，会话内无关工作不受影响。详见 [暂停契约](monitoring-pause-contract.md)。

旧 WatchProgram、来源与监控 HTTP 接口保留；旧监控按有效暂停/结束状态归类。用户结束最后一个独立后台目标时，Dashboard 停止其 Task 下的 Main/工作；会话内结束只影响该目标。

修改从 [代码地图](code-map.md) 定位生产者、消费者与回归。相关入口为 [领域与持久恢复](../test/long-term-goals.test.js)、[真实 Pi 目标工具](../test/goal-tools.test.js) 与 [暂停](../test/monitoring-pause.test.js)。P4.5 已移除目标与监控的界面入口，界面验收用例随前端模块删除。这些是验证入口，不表示当前版本已执行或通过。实际模型、真实来源、macOS 服务和多周驻留分别验收，结果绑定版本与环境写入 PR 或发行记录。
