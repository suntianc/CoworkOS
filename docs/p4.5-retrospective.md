## 阶段内修复与经验

### 1. 审查抓到的真实缺陷

- #16 发现分屏协作布局失效：`is-collaborating` 加在 `.chat-body` 上，网格规则却写在 `.chat-pane.is-collaborating .chat-body`，分隔条只有 6×0。缺陷在 #14 修复。
- #14 发现窗口窄于 640 时，关闭设置后焦点丢失：设置入口位于已关闭的侧栏抽屉内。修复后焦点回到抽屉开关。
- 终审 A1：同一 Task 第一次收到详情时面板被重置，项目 id 晚到时也会丢弃已加载的记录。修复后同 Task 重载时保留上一次记录；回归测试延迟首次详情读取，旧代码 3/3 失败，新代码 3/3 通过。

### 2. "偶发失败"多数是测试自身的问题

- `request-recovery` 的偶发失败：测试假服务器对 Buffer 用 `raw += chunk` 拼接，多字节字符在块边界被切断（"谱系"读成"谱���"）。e2e/ 与 test/ 中同类写法共 38 处，统一改为 `setEncoding("utf8")`。
- `computer-use` 测试读取本机真实的屏幕录制、辅助功能授权，在已授权的机器上必然失败；改为固定 `/api/computer/status`。
- `markdown-links` 的偶发失败暴露了产品问题：输入框在应用就绪前已可输入，草稿恢复会覆盖已输入的文字。见打磨清单第 19 条。

后续遇到偶发失败，先单独重复运行并读取失败现场，区分测试缺陷、产品竞态和环境问题，不直接判为负载抖动。

### 3. 测试重复导致合入很慢

每次 integrate 都会跑公共检查（`npm ci`、安装 Electron、`verify`）以及全部回归命令。回归集中，全量 Playwright 已包含约 30 个单独的 spec，`verify:full` 已包含 12 个单独的 Node 测试文件；候选树与审查时一致时仍从头再跑；任何失败都整体回滚、整体重跑。#14 因此合入了 6 轮，每轮 20–30 分钟。

用户确认今后的做法：只测改动相关的部分；失败后只重跑失败项；全量只在合入 main 前或终审时跑一次，收尾复用同一提交上的全量证据。工具层面的建议见 [WL-11](workloop-followups.md#wl-11-合入与收尾的重复检查)。

### 4. 长时间检查前先预检环境

有 3 轮检查因环境问题白跑：Docker 守护进程停止（PostgreSQL fixture 退出，Node 套件出现 1–48 项失败）、屏幕锁定、本机电脑操控授权。`verify:full` 还需要 `COWORK_PYTHON` 指向已安装 fitz/docx/pptx/openpyxl 的解释器（见 [开发环境](development.md)）。开始长时间检查前，先核对 Docker、解释器、锁屏状态和机器负载。

### 5. 票面格式

Scope 行中带中文括注时会被误解析，#19、#20 因此被审查拒绝。Scope 只写纯路径，例如 `web/, desktop/, test/, e2e/, docs/`。

## 用户决定

- 推理强度：手动修改只作用于当前会话，不影响其它会话（#19）。
- 去掉星空动画（#20）；Web 端使用纯色背景，桌面端透出系统材质（#15）。
- 桌面端测试默认在后台运行，不抢占前台（#21，`FORMICAND_DESKTOP_BACKGROUND=1`）。
- 集成门禁中的 Playwright 以单并发运行，不放宽断言（#16、#20）。
- 未配置模型时的 Pi 扩展 unknown task 修复放到 P9（#22 取消）。
- 新增 P4.6「Pi 运行时升级与架构决定」；按供应商配置模型并自动探测模型列表，放入 P4.6 一并定方案。
- 后续界面打磨由 Main 直接完成，不再派单。
