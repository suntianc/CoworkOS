# P1 复盘：独立后端与统一管理协议

日期：2026-11-06。本文记录 P1 的验证经验和后续开发采用的做法。

P1 交付分支为 `workloop/os-p1-backend`，验收提交为 `d4417d7a6a30529b79e3c21ffb4dd93e0e377c61`。五张票均已集成，独立终审与最终交付检查通过；没有豁免阻塞发现、修改验收标准或超过返修轮次上限。

## 验证范围

P1 覆盖独立后端生命周期、执行主机凭据、授权与幂等管理命令、快照及事件恢复、浏览器共用管理客户端。现行接口见 [Product API](product-api.md)，环境和检查入口见 [开发指南](development.md) 与 [本地测试](testing-local-run.md)。

- `npm run verify` 及累计 16 条验收命令通过，五个专项文件分别是 `os-daemon-lifecycle`、`os-backend-settings`、`os-management-commands`、`os-event-recovery`、`os-web-client-protocol`。
- Chromium 153 的 20 步浏览器验收使用两个真实后端、真实 Pi 和本地模型 fixture，覆盖后端切换、授权失效、草稿恢复、关闭页面后任务继续执行、重开读取和产物下载。两份下载内容的 SHA-256 与源文件一致。
- 旧配置迁移通过 macOS Electron safeStorage 与 keychain-worker 路径验证，使用 `--use-mock-keychain`；真实钥匙串授权提示未验证。
- 全量测试曾出现环境、既有用例和本次回归等不同失败；最终结论以明确执行通过的检查与修复回执为准。Electron 升级、原生打包、真实模型账户、跨机器远程连接及 Windows/Linux 尚未验收。

## 1. 浏览器调试反复启动整套流程

**发生了什么：** 前端票首轮启动浏览器验收脚本 16 次。部分执行跟随实际修复，部分只是为了重新截取错误输出。后者重复支付了启动后端、建项目、执行任务和等待超时的成本。编排者直到用户指出耗时后才收窄检查并设置 15 分钟检查点，介入偏晚。

**采用的做法：** 首次运行保存完整 stdout、stderr、退出码和候选提交，再从日志中提取需要的片段。定位时运行最小失败场景；修复后在最终候选上验证受影响的验收路径。长时间无结果时检查具体阻塞和新增证据，再决定是否继续。

日志中的“查看另一段输出”不构成重新执行测试的理由。新的行为改动、失败或未解决的风险才触发额外验证。

## 2. 验收条目无意中重复了同一测试

**发生了什么：** 五个测试文件对应了 16 次命令执行：生命周期 4 次、设置 3 次、管理命令 4 次、事件恢复 4 次、前端协议 1 次。累计回归继续保留这些次数，五次集成检查共约 28 分钟；最终交付检查约 6 分钟。

**采用的做法：** 下一阶段确认票据时，同时列出不同检查命令和完整回归中的执行次数。不同功能可以使用聚焦命令；同一套测试覆盖多个行为时，可以在验收仍清晰的前提下合并条目。稳定性、时序或外部状态验证所需的重复执行，应明确写出目的和次数。

P1 已确认的验收保持原样；本条用于后续票据设计，不回溯减少已约定的检查。

## 3. 共用模块改动漏查了较远的调用方

**发生了什么：** 主机凭据迁移最初漏了监控启动器读取有效配置、以及会话导出时收集主机密钥进行脱敏。前端下载改造新增全局拦截器后，又误拦了本地生成的 Markdown `blob:` 链接，导致导出请求后端并返回 404。

**修复与证据：** 凭据相关消费者已改用有效主机配置，相关回归覆盖在 [设置测试](../test/os-backend-settings.test.js) 和 [监控启动测试](../test/watch-supervisor-launcher.test.js)。下载拦截器只接管根相对 `/api/` 路径，保留 `blob:`、`data:` 的浏览器行为；[页面启动测试](../test/app-boot.test.js)、[会话菜单浏览器测试](../e2e/conversation-menu.spec.js) 与 [产物链接测试](../e2e/markdown-links.spec.js) 验证了修复。

**采用的做法：** 修改配置来源、鉴权、公共网络层或下载路径前，沿 [代码地图](code-map.md) 列出生产者和消费者，检查 CLI、后台进程、Web 与桌面入口。网络产物和页面本地生成文件分别验证，避免只覆盖新增的正常路径。

## 4. 对测试失败的归因过于笼统

**发生了什么：** 前端票最初把抽查到的广泛浏览器失败归为基线或环境问题，但其中包含本次引入的 Markdown 导出回归。独立审查复现后修复，报告也更正了归因。终审的新工作区另因缺少依赖和数学排版生成资源而先失败，补齐前置条件后通过。

**采用的做法：** 对每个已观察的失败分别记录“本次回归、基线已有、环境或前置条件、尚未确认”，并附对应证据。基线判断应有同条件对照；前置条件判断应有具体缺失项与补齐后的结果。尚未确认的项保留原始失败，避免从部分抽查推导整个套件的状态。

新工作区按开发指南准备所选检查的依赖和生成资源。静态检查通过后，仍需确认浏览器或原生场景所需产物已生成；相关检查通过后，按实际变化决定后续验证范围。

## 后续阶段要带入的事项

以下保留 P1 终审时的观察。2026-11-07 更新：三项均已由 P2 接续处理，当前实现与回归入口见 [落实索引](retrospectives.md#已修复并有回归覆盖)。

- **统一桌面与后端启动所有权：** 旧 `dashboard` 入口未发布独立 daemon 的实例记录；与 `backend start` 共用同一数据根时存在双服务写入风险。P2 需统一发现、复用和关闭行为，并验证同根重复启动。
- **不同后端的授权接入：** 当前本机跨端口浏览器验收使用相同的合成 bootstrap 凭据；不同主机凭据的后端会进入未授权状态，需明确宿主接入流程。
- **产物打开入口：** 抽屉的“打开”链接仍指向页面所在后端，切换后端时需核验它与授权预览、下载的归属一致。

## 保留的有效做法

独立审查发现了执行自检遗漏，返修后有独立复验；集成与终审绑定候选提交，失败和成功证据分别保留。原工作区及已有改动保持完整。继续采用这些做法，并通过更精确的用例选择和日志留存减少重复成本。操作入口已归入 [开发交接与验证记录](development-handoffs.md)。
