24. 【缺陷，已修】Agent 输出（流式）时滚动主面板会闪屏。
    - 原因：不是第 17 条的 `content-visibility`（关掉后照样复现）。发送后本地乐观消息要等详情里出现已保存的用户消息才清掉，整轮运行期间都在；渲染时只要它在，就把滚动位置设到底。流式每来一段渲染一次，用户往上滚一下就被拉回底部，来回跳就是闪。
    - 修法：发送新消息时只滚到底一次（记住已跟随的那条本地消息），之后按读者位置决定是否跟随（离底部 100px 内才跟随）。
    - 测试：`e2e/p45-stream-scroll.spec.js`（去掉修复会失败）。录屏比对：修后向上滚动不再有回弹帧。
25. 【已做】发送按钮没有按设计稿（第 9 条画板）重做：需对照设计稿逐项核对尺寸、形状、图标、颜色与运行中/可插入/可排队各状态。

    - 点模型名进入模型列表：标题「选择模型」，列出可选模型，当前项打勾。
    - 参考图来自其他产品，只借鉴交互结构，界面元素沿用本产品的样式与文案。
    - 设计稿：「打磨 27 · 深色 / 浅色 · 模型与推理强度」与说明栏（2026-11-12）。
    - 档位随模型（用户已定，2026-11-12）：不同模型支持的推理档位不同，滑块只显示当前模型支持的档位。官方厂商地址自动识别：连接的 API 地址与 Pi 内置模型表（`@earendil-works/pi-ai` 的 `getSupportedThinkingLevels`）中某个厂商的地址同主机时，按该厂商下这个模型 ID 取档位，表里没有这个模型时给全部档位；其他地址在连接设置「高级连接参数」里自己勾选支持的档位（默认全选、至少一项，作用于该连接下所有模型）。连接默认推理强度只能从支持的档位里选。档位来源按顺序：① 服务商 `/models` 接口返回的模型配置（如 `reasoning_levels`、`supported_reasoning_levels[].effort`、`reasoning: false`，按模型；用户补充，2026-11-12）；② 上述官方厂商地址查 Pi 模型表；③ 连接设置里手动勾选。同一份接口配置里的上下文容量、输出上限、图像输入也识别为该模型的默认值，连接里手动填过的优先。Pi 不认的档位（如 `ultra`）不显示并在设置里说明。换模型后原档位不支持时取最接近的一档并在浮层里说明一次。此前的需求在档案里只有「确认支持的推理强度参数」一句，没有落成任务，此处补记。

## 第 17 条性能基准（2026-11-11）

测法：`npm run test:perf`（`e2e/perf/conversation.perf.js`，`PERF_ROUNDS` 默认 200）。先真实跑一轮（两次工具调用 + 带表格、40 行代码、任务清单的长回复），再在磁盘上复制成 200 轮，页面按真实历史读取。测四段：打开会话、空闲 10 秒、从顶滚到底、在末尾流式输出 400 段。结果写到 `test-results/perf/`。1440×900，Chromium，开发机（负载约 5）。

| 指标（200 轮）                 | 优化前           | 优化后                              |
| ------------------------------ | ---------------- | ----------------------------------- |
| 会话详情响应体                 | 57 MB            | 7.5 MB                              |
| 打开到全部渲染                 | 约 2.0 s         | 1.2 s（等后端 0.6 s，主线程 0.2 s） |
| 打开时最长任务                 | 390 ms           | 116 ms                              |
| JS 堆                          | 263 MB           | 44 MB                               |
| 滚动：帧 p95 / 超过 50 ms 的帧 | 16.8 ms / 7      | 16.8 ms / 1                         |
| 流式：帧 p95 / 超过 50 ms 的帧 | 83 ms / 89       | 16.8 ms / 3                         |
| 流式：主线程占用               | 80%              | 24%                                 |
| 流式：长任务                   | 105 个，共 7.4 s | 2 个                                |

改了三处：

- 详情和事件流里，系统提示词的开始/结束事件和 `agent_end` 只保留事件本身，去掉正文（每轮都带一整份系统提示和消息列表，占详情的近九成，页面不读）。
- 会话列表按轮次记住上次的标记和节点数，流式更新只从第一处变化的轮次往后打补丁，之前的轮次不再整段解析、比对。
- 末尾 4 个以外的轮次用 `content-visibility: auto`，屏外内容跳过样式与布局。

### 待做的优化（2026-11-11 记录，后面做详细测试再定）

1. 后端每次读会话详情都全量回放所有 Run。
   - 原因：每次空闲时发消息就开一个新 Main Run（`<会话>/runs/<runId>/`）；思考、工具步骤和耗时只记在各 Run 的 `runtime-output.log`，要显示整段执行过程就得读所有 Run（并行读，主要耗时在逐行解析和拼 JSON）。页面每隔几秒轮询一次详情，后端每次都重做一遍。
   - 现状（200 轮）：打开时约 0.6 s 在等后端。
   - 方案：已结束的 Run 文件不再变化，后端按文件大小/修改时间缓存解析结果，只重读正在运行的那一个；对页面透明。
2. 详情里约 4 MB 是流式中间数据。
   - 原因：流式时每段输出一条 `message_update`（带当时的部分消息），结束时 `message_end`、`turn_end` 又各带一份完整消息。（200 轮：`message_update` 1.9 MB，`turn_end` 1 MB，assistant 的 `message_start`/`message_end` 各约 0.9 MB。）
   - 页面在用：执行过程的顺序、各步耗时、中途打断的状态靠这些事件还原。
   - 方案：已结束的轮次只保留最终快照；需逐一确认界面还原一致，涉及 `thinking-display`、`execution-display` 等测试。
3. 分页加载 / 虚拟列表。
   - 现状（200 轮）：页面元素约 6.2 万、JS 堆 44 MB，滚动和流式都 60 帧，打开时主线程 0.2 s，暂不需要。
   - 触发条件（看指标，不看轮数；真实一轮常有十几、二十次工具调用，分量可抵测试里的五到十轮）：JS 堆超过约 200 MB、打开时主线程超过 1 s，或详情超过约 30 MB。
   - 方案：先做历史分页（打开只取最近 30–50 轮，滚到顶再加载更早的），可同时缓解 1、2；虚拟列表代价大（滚动条估高、页内查找、跨轮选中、焦点与展开状态、渲染缓存都要重做），放最后。
4. 详细测试：用真实长期使用的项目会话量出 Run 目录数和详情大小，再用 `PERF_ROUNDS` 和每轮更多工具调用按该规模复测，然后决定 1–3 做哪些。
