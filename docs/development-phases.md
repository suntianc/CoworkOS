## 已确认的产品规则

- UI 服务于运行观测、管理和本地工作；对外后端能够独立自动接单。对内与对外 Main 分开，暂按不同服务器部署；对内 daemon 可以离线。
- 需求台账提供项目上下文；需求看板发布任务、记录认领归属、归属人和处理 Main。对内新需求直接进入台账，认领已有看板需求时才更新看板状态。
- 对外服务的 Main 运行名额固定分为常驻与接续，常驻禁止借用接续名额，对内 Main 不计入该上限。每个项目的对外常规会话上限等于服务常驻名额数；接续会话另计。保存而未运行的会话不占名额，新需求按空闲分派。
- 会话属于项目，运行名额可以先后加载不同项目会话。回访等待时保存需求分支并挂起；收到回复后由新的接续 Main 继续，完成或再次挂起后退出。
- OS Main 自主决定调查、方案、委派和开发通道。Workloop 的通道条件作为建议，重点引入完成标准、按需独立审查、版本与证据、返修复审及完成判定；全部使用 OS 原生 Agent 调度。
- 容量限制只作用于 Main；Main 下的 Executor、Reviewer 及其他子 Agent 不设数量或并发上限，由 Main 按工作需要组织。
- 对外 Main 认领的需求按对外流程处理回复；用户通过对内 Main 认领的需求，将回复发送给归属人配置的聊天通道。
- 首次提问后最多追加 3 次回访。第 3 次后再等一个周期仍无回复，停止回访、标记并通知项目负责人；保留需求归属，由负责人决定后续处理。
- Main 修复并合入后完成开发；看板标记“待发布”并关联实际合入的 commit。发布后凭证据批量更新覆盖到的需求。

## P3：项目共享数据与多 Main 基础

本阶段建立后续工作共同使用的身份、数据和运行基础。

- 建立项目、需求、看板条目、归属人、Main 会话和运行名额之间的明确关联。内部新需求与看板认领沿用各自入口规则。
- 前移需求台账的最低可用读写和查询：需求内容、有效决定、来源、版本与后续交付引用。台账与看板分别建模，通过需求关联。
- 为对内、对外后端提供统一的共享数据访问入口，明确数据权威和更新规则；各自保存运行目录与执行状态。支持 SQLite / PostgreSQL 可选存储：个人维护默认使用 SQLite，需要独立数据库服务时显式选择 PostgreSQL。两种模式共用领域服务与业务接口，台账、看板、认领和恢复行为一致；已有历史记录保留兼容读取。
- SQLite 由权威服务持有本机数据库文件，其他后端通过业务 API 共享；PostgreSQL 模式沿用同一 API，由权威服务连接数据库。选择作用于服务启动，说明各模式的配置、数据库版本迁移及备份恢复；数据库凭据留在服务端。
- 实现常驻/接续名额配置及容量约束，接续名额先保留；事件驱动的 fork 接续在 P5 接通。实现常规项目会话的按需创建、保存、恢复与跨项目切换。
- 提供模型连接与角色选择的共同配置基础，先接通 Main；Executor/Reviewer 在 P4 使用，Router 在 P5 使用。已交付的优先级和生效规则见 [配置参考](configuration-reference.md)。
- UI 具备项目工作入口、会话列表、基本看板与名额状态。信息架构从本阶段开始，功能新增时同步可用交互。

阶段验收：使用多个项目和独立内外后端实例，验证同项目多会话、全服务容量限制、跨项目恢复及共享认领状态；验证对内新需求仅进入台账。SQLite 与真实 PostgreSQL 执行同一组核心存储行为检查，覆盖持久化、修订、事务和竞争认领；重启后会话、归属与名额能够对账。共用 UI 和完整套件按实际影响验证，避免为数据库模式重复整套采样。此阶段可以通过受控输入验证基础流程，真实外部渠道在 P5 验收。

## P4：OS 原生开发与验收

本阶段完成首个实际开发里程碑 M1：用户在 OS 中提出需求，Main 完成开发、必要验收并合入。

- 保留 Main 动态调查、选择方案和委派的行为，使用 Workloop 的轻重流程建议；在任务开始时记录完成标准。
- 接通执行与审查角色的模型配置。需要独立审查时，由 OS 启动 Reviewer；简单工作按相应验证方式收尾。
- 把验收对象、结果版本、检查回执、审查发现和返修结果持久关联。复审围绕原问题与新增改动，验证范围与实际影响匹配。
- Main 对审查范围争议或误报作有依据的裁定并保留理由；改变已确认需求、验收标准或业务取舍时由项目负责人决定。
- 沿用 Workloop 的隔离现场、固定候选审查、原执行上下文返修和依赖调度规则。多个 Main 的需求通过项目共同入口串行合入到配置的目标分支，开发工作继续并行；验收覆盖实际交付版本。执行与恢复复用 OS 运行管理，不搬入 Rex 或多 CLI 编排。
- Main 修复、验收并合入后结束本次开发；已有看板需求更新为“待发布”并关联实际合入 commit，对内直接提出的需求把交付记入台账。
- UI 展示执行、审查、返修和合入结果，代码交付以提交、diff、验证结果为主，附件按需提供。

阶段验收：完成至少一项真实模型参与的 OS 开发任务；覆盖自主执行、按需独立审查、返修后通过、多个需求的改动隔离与合入，以及合入提交和待发布记录一致。已按冻结的 A–F 场景完成六票 12 条 AC，并以补修 #07 的 3 条 AC 修复真实验收暴露的命令 stdin EOF 问题；版本、人工介入与证据复用范围见 [P4 交付与验证](p4-retrospective.md#交付与验证)。

## P4.5：UI 与交互打磨

在已有开发闭环上集中打磨 UI。保留两个清晰用途：工作入口用于与 Main 协作；观测入口用于查看节点、项目、需求、会话和运行状态。界面术语统一为“节点”，不再使用服务/daemon 字样。

- 界面分为工作、观测两个入口与设置。工作入口只使用本机节点，侧栏按“项目 → Main 会话 → 子 Agent”树组织：项目可折叠并显示会话数，子 Agent 挂在所属会话下并标记角色。会话的阶段与状态细节只在右侧需求进度卡片呈现，侧栏仅在 Main 向用户提问、等待回答时为该会话显示提示点。
- 工作入口提供明确的新会话入口；项目通过侧栏加号添加，P4.5 支持选择本地目录或填写 Git 地址克隆到本地（使用用户已有的 Git 凭据，GitHub、GitLab 与自建仓库通用）。代码托管账号登录、仓库浏览及 Issue/PR 关联在 P7 处理。
- 观测入口聚合所有已连接节点，侧栏依次为视图（总览、需求、运行）、节点列表与项目列表；选中节点或项目即筛选当前视图。观测只读呈现状态，不提供打开会话与查看 diff，不在工作入口执行远程工作。从远程看板领取需求（读取需求资料后与本地 Main 讨论设计开发）不在 P4.5 实现，待认领需求仅展示。
- 观测“总览”按节点展示运行与名额状态、各项目需求按阶段的数量分布、需要人工介入的事项与正在运行的 Main。
- 观测“需求”将台账、看板与开发现场三个弹窗合并为列表加详情页，项目范围跟随侧栏筛选；详情为通用结构，阶段条高亮当前阶段，改动只显示文件与行数统计。修复已交付需求仍显示进行中的状态映射，内部路径与 Agent 内部标识退居辅助信息。
- 会话右侧任务面板改为“需求进度”：阶段、完成标准、改动与附件为主，用量与执行细节按需展开；附件与 diff 在工作入口内按需打开。删除智能体星系及其成员记录、执行轨迹展示。
- 统一项目、会话、看板、开发验收与待发布信息的导航和层级。
- 将节点连接、角色模型、名额、归属人和通道配置组织到明确的设置位置；设置改为带导航的分区页（通用、节点连接、模型与角色、运行名额、成员与通道、工具），本机与远程节点分开管理；常驻/接续名额只对远程对外节点配置，本机节点不配置名额。成员与通道页中属于 P5/P7 的通道与回访能力在 P4.5 以占位呈现，随实现逐步开放。
- 完善首次使用引导与空状态（含未配置模型连接），以及切换、暂停、取消、错误恢复及结果查看的反馈；减少旧应用工作台留下的无效入口和说明。工作台与应用入口移出主导航，附件按需打开，底层应用与资源协议保留。
- 长期任务（长期目标与监控）只保留后端能力与接口，移除界面入口；产品中的使用方式日后单独规划。
- 视觉层统一为低透明度玻璃底板加悬浮卡片的质感；桌面端可使用系统窗口材质并直接透出，Web 端为纯色背景（深色近黑、浅色近白）；动效遵守系统减少动态效果设置；提供深色与浅色主题，并适配窄窗口。产品标志更新为五节点拓扑标，含无连线的小尺寸变体；界面显示名称在本阶段改为 Formicand，安装包、CLI、配置目录、仓库与包名等保持不变，留待 P9 彻底清理。
- 观测聚合需要每个已连接节点各持一条只读连接并在前端汇总；当前管理客户端为单后端绑定，需扩展为多连接聚合。跨机器节点的连接与远程验收沿用 P6 边界，本期至少支持本机多个节点的观测。
- 观测入口的“运行”以脉冲泳道呈现各节点正在运行的 Main：每个 Main 一条泳道，按时间窗口显示活动波形与阶段颜色，子 Agent 作为分支；对外节点按常驻/接续名额分组，空名额显示为平线，长时间无进展的 Main 突出显示。排队与已保存会话不在此视图。实时波形需要后端为每个 Main 提供可跨节点读取的活动指标（如工具调用与输出速率）；指标就绪前以阶段色块与持续时长的降级形式呈现。
- 基于真实试用验收首次使用、日常开发和状态查找。P5/P6 随功能追加交互，继续遵守同一设计。

阶段验收：用户能找到工作入口，完成一次开发交互，查明需求由谁处理、停在哪一步，并找到合入结果；常用路径无需依赖开发者解释。

## P4.6：Pi 运行时升级与架构决定

运行时的 Agent 循环、模型接入、Main 会话与上下文压缩依赖 Pi（`@earendil-works/pi-coding-agent`、`pi-agent-core`、`pi-ai`），当前锁定 0.87.1，上游已发布 1.x（规划时为 1.5.1，2026-11-12 为 1.5.2），并新增了 MCP 等内置能力与插件机制的变化。本阶段先评估、形成架构决定并由用户确认，再按决定实施，避免 P5 起继续在旧接口和自建替代上叠加。评估以 P5 的挂起、fork 与接续需求为输入，使 Main 不在进程中时的会话状态与名额归属只定一次。

- 能力与变更摸底：梳理当前版本至目标版本的变更与新增内置能力（如 MCP、插件与扩展机制、会话与压缩、工具与权限模型），列出影响现有扩展钩子与触发顺序、事件格式、CLI 参数、`pi-agent-core` 与 `pi-ai` 接口的不兼容改动；在独立分支试升级并运行真实 Pi 进程测试与全量回归，作为评估证据。同时验证数据方向：旧版写入的会话、任务与上下文由新版读取，以及新版写过的数据能否由旧版读回，据此确定回滚方式。
- Pi 接触面盘点：列出自有代码直接使用 Pi 的位置。当前 65 个非测试文件直接导入 Pi，其中 9 处使用包内深路径（如 `pi-agent-core/harness/context`、`pi-ai/api/*.lazy`、`pi-ai/providers/all`、`pi-ai/utils/transcript`）；`scripts/start-pi-runtime.mjs` 解析包内的 `bundle/cli.js`；`src/storage/main-request-store.ts` 的持久记录直接使用 `pi-ai` 的 `Context` 与 `Model` 类型。逐类标注上游是否承诺稳定，以及升级时的改动量。
- 架构评估：逐项比较自有实现与新版 Pi 能力——工具接入与 MCP、插件/扩展的增删与组织方式、技能与提示词、Main（Pi CLI 子进程加扩展）与 Subagent（进程内 `pi-agent-core`）两套执行循环、Main 的双份上下文与压缩钩子、子进程生命周期与名额绑定、两套基础工具的权限与超时规则；结合历史缺陷与 P4.5 打磨记录，给出采用、保留、替换或删除的选项及代价、风险与迁移影响。
- P5 需求作为评估输入：P5 要求回访等待时保存会话分支并挂起、释放名额，回复到达后由接续 Main 继续。对照新版 Pi 的会话与 fork 能力和现有 `src/runtime/conversation-fork.ts`，确定会话分支的保存、fork 与恢复由谁实现。名额当前随 Main 进程退出释放（`src/dashboard/run-service.ts`），账本是单机文件（`main-capacity/state.json`）；评估须回答 Main 不在进程中时名额是否保留、被占用后回调与回复如何排队，以及存在多个对外节点时项目会话上限由谁裁决。
- 无人值守执行的权限：P5 的对外 Main 无人值守处理客户消息并具备命令执行与合入权限，而现有 `GrantedPermissions` 不证明 Pi bash/jobs 受 OS 沙箱隔离（见 [架构](architecture.md#信任边界与支持范围)）。已确认最低隔离前置到 P5，随首个真实渠道一起交付。本阶段评估新版 Pi 的工具与权限模型能否承担这部分隔离，确定由 Pi 内置能力、自有实现或 OS 沙箱实现，并给出各方案的代价与未覆盖范围。
- 模型供应商配置（P4.5 试用反馈）：模型连接从「一个连接一个模型」改为配置供应商（API 地址与 Key）后自动探测模型列表，角色绑定改为选择供应商下的模型，并迁移已有连接。P4.5 打磨 #27 已交付按模型取值的部分：思考强度档位取 `/models` 返回，缺失时取 `pi-ai` 内置目录；上下文长度、输出上限与图片输入取 `/models` 返回，手动填写优先。本阶段的剩余范围是供应商实体、存储结构迁移、角色绑定，以及接口未返回限值时的厂家默认值（评估沿用 `pi-ai` 内置目录）。该项只在默认值来源上依赖 Pi，可独立于升级排期。
- 子代理执行时 Main 空闲（P4.5 试用反馈）：当前 `call_subagent` 的执行器（`CoordinatorRuntime`）建在 Main 的 Pi 进程内，Main 又常以 `sync` 方式等待结果，所以子代理执行期间 Main 进程和运行一直挂着，界面也一直显示运行中。分两步处理：先把 Main 的状态拆成工作中、等待子代理、空闲，供工作页与运行看板显示，这一步不改变执行器位置；再评估改为后端常驻子代理执行器（现有 `src/runtime/worker.ts` 只在 CLI `cowork worker` 中使用）、Main 以 `async` 派单后停下、子代理回调由 Main 守护（`src/runtime/main-supervisor.ts`）唤醒。评估须比较唤醒延迟与成本：现有异步回调在进程内立即投递，而 Dashboard 的 Main 守护默认 60 秒轮询一次，停下后的 Main 还要重新启动 Pi 进程并重载上下文；采用该方案时唤醒改为事件驱动。同时评估对插入消息、暂停与取消、名额占用和恢复的影响，名额部分与上一项 P5 输入一并决定。
- 架构决定：形成决定记录，明确对 Pi 的依赖边界、采用的 Pi 内置能力、需新增或删除的插件与扩展、收敛或保留的自有实现、升级与数据迁移及回滚方式，以及后续版本的跟进办法；不修改上游 Pi 源码的约束是否保持也在此确认。依赖边界写成可检查的规则：允许导入 Pi 的模块清单、是否允许包内深路径，以及持久格式是否改用自有类型，由 ESLint 或架构回归约束。评估结论可以是整体升级、部分升级或暂不升级，各自写明理由与后续条件。决定经用户逐项确认后才进入实施，实施切片与对应验收在确认后细化。
- 实施顺序：先完成行为不变的升级并通过回归，再按决定调整架构，两类改动不放进同一切片；模型供应商配置与 Main 状态拆分可在决定确认后独立排期。

阶段验收：架构决定记录覆盖上述各项并经用户确认；按决定完成升级与调整，真实 Pi 进程测试、全量回归与真实模型开发闭环通过，已有会话、任务与上下文数据可继续使用，回滚方式经过实际验证；依赖边界规则已由静态检查执行；未采纳与暂缓项有记录和理由。

## P5：对外接单、回访与接续

本阶段完成对外自动化里程碑 M2。建议首个真实渠道采用飞书，覆盖接单、客户回访和负责人/归属人通知；具体首选渠道在本阶段细化时确认。

- Router 接收来源事件，关联项目与需求，将识别出的需求登记到看板；Main 自主分析和推进，按已定边界请求负责人决策。
- 将外部回复准确关联到问题、需求和当前认领归属。对内认领后按人的通道配置转发，个人笔记本离线不影响服务端处理消息。
- 回访或确认信息发出后，保存会话分支及工作进度、挂起需求；常驻名额继续接单。回复到达后使用专用名额创建接续 Main；再次等待则保存最新分支并退出。
- 实现定时回访和 3 次上限、超限标记及负责人通知。间隔可配置，具体默认值在本阶段确定。
- 实现首条跨机器、认证的共享数据访问与消息链路。对内与对外运行目录独立，离线及恢复后归属一致；完整远程管理和平台交付在 P6 验收。
- 为不可信输入提供最低隔离（实现方式按 P4.6 决定）：对外 Main 处理客户消息时，命令执行限定在该需求的隔离现场内，不能读取节点凭据、模型密钥和其他项目的数据；合入与对外发送由程序侧按需求归属校验，不以消息内容中的指令为依据。未覆盖的范围逐项记录。
- UI 展示等待对象、回访次数、接续状态和归属；程序处理重复事件、发送回执和恢复，Main 判断内容与下一步。

阶段验收：真实渠道进入需求；模拟并实际观察客户延迟回复后 fork 接续；再次回访释放名额；次数耗尽后通知负责人；对内认领后关闭本地 daemon，消息仍送达其配置通道。全过程保持常驻与接续名额隔离。用含指令的客户消息验证：对外 Main 不能读取节点凭据和其他项目数据，也不能越过需求归属合入或对外发送。

## 下一步与验收原则

P3 已完成默认 SQLite、可选 PostgreSQL、统一接口、角色模型配置、看板控制与兼容策略的验收。P4 与 P4.5 已按各自验收完成并归档，P4.5 的试用打磨仍在进行；下一步是 P4.6 的能力摸底与架构评估，形成决定记录后由用户逐项确认。各阶段启动前细化并确认实施范围与验收用例；首个外部渠道、回访间隔和发布证据来源按对应阶段安排。本规划不设置票数、工期或未经测量的并发默认值。

实施沿用 [开发交接](development-handoffs.md) 与 [本地测试](testing-local-run.md)：按改动运行相关检查，阶段末验证组合行为；仍有效的证据复用，候选回归、基线、环境和未知失败分别记录。全量、原生、实际模型及安装验证在相应验收点安排，避免同一版本反复采样。

P1、P2 与科学剪枝的归档状态及原始证据保持原样。移动端原生 App、通用跨机器执行集群、完整团队多租户及额外模型运行后端继续单独规划。
