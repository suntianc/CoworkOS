# P2 复盘：Electron 桌面接入与交付

日期：2026-11-07。本文记录 P2 的交付结果、返修原因和后续开发可采用的做法，接续 [P1 复盘](p1-retrospective.md)。

P2 交付分支为 `workloop/os-p2-electron`，验收提交为 `7f6c215311106ab365a1a13a98a570a5456407c8`。六张票均已集成，独立终审、最终交付检查和归档完成；没有豁免阻塞发现。第二张票的一次超上限返修经用户授权，第六张票的干净账户验收经用户同意后移 P6。

## 验证范围与结果

P2 覆盖 Electron 45.2.3 接入独立后端、草稿与附件恢复、宿主管理凭据和设置、移除语音输入、执行主机权限边界，以及本地包和资源占用验收。现行接口与流程见 [Product API](product-api.md)、[代码地图](code-map.md)、[本地测试](testing-local-run.md) 和 [Mac 发布](mac-release.md)。

- 最终同一源码树的 `npm run verify:full` 记录为 2,896 tests、2,839 pass、0 fail、57 skip。第二轮终审的 `npm run verify` 和六条专项命令通过，专项合计 124/124，无跳过。
- 保留实际后台任务、附件、设置、真实原生权限与钥匙串回执；未受本次改动影响的既有证据按验收映射复用。当前账户内使用隔离数据与安装目录完成安装验收；干净 macOS 账户安装和系统权限验收由 P6 承接。
- 最终包的三次冷启动为 880/977/973 ms，中位数 973 ms；三次热启动为 552/588/563 ms，中位数 563 ms。空闲客户端与后端 RSS 中位数分别为 616.7 MiB、136.8 MiB，按进程角色分别统计。
- 保留 `CoworkOS-0.1.3-mac-arm64.dmg`，大小 176,047,042 bytes，SHA-256 为 `483e1da96cef0e331b179a2ea88018e5dc1fa25c1884d736ed2df01fbb35e292`。ad-hoc 深度严格签名检查通过；Developer ID 签名、公证、真实外部模型连接及 Windows/Linux 未验收。

全程有 16 次票据审查、2 次终审、2 次执行者替换和 1 次集成失败；没有集成冲突。六次成功集成检查合计约 3 分钟，大量耗时出现在实现、原生验证、诊断和返修阶段。后续应优先改进交接和验证选择。

## 1. 本机原生步骤应由主代理提前接手

**发生了什么：** 第一张票的原生检查多次遇到旧导航假设、草稿格式变化和真实系统认证要求。执行者后续报告已给出可执行的本机交接，主代理仍将“等待主代理完成”视为整体阻塞，导致用户授权无人值守推进后任务停顿。之后由主代理持有隔离 App 与后端，完成真实 LocalAuthentication 和自有窗口验证，关闭了该缺口。

**采用的做法：** 派发前明确系统认证和桌面操作的负责人。执行者交付现成候选、已有证据和具体未完成步骤，主代理接手可执行的部分，并继续不依赖用户的工作。沿用已有授权；实际需要用户认证时，再提出该项具体需求。

这项经验用于任务交接和编排，不增加产品中的审批流程。

## 2. 草稿恢复需要同时处理数据、占用和入口

**发生了什么：** 第二张票的恢复状态过早从 `ready` 改为 `live`，进程中断后已保存内容失去恢复入口；多个旧草稿组也缺少可操作的逐组选择。只添加状态标记没有覆盖保存、占用、迁移、冲突和来源清理的完整生命周期。

**修复与经验：** 最终以持久化的 `ready` 状态、独立的活跃租约和逐组恢复入口解决问题，并覆盖迁移提交及来源保留、删除规则。现有回归包含真实进程退出和 UI 恢复路径。后续 P3 引入 Request 时，应复用这套状态和消费者，明确数据恢复责任与活跃占用的关系。

已有顺序表和生命周期回归继续维护；相同行为无需再增加重复测试。

## 3. 验证范围按候选变化收敛

**发生了什么：** 第六张票初期把八项历史失败清零、性能诊断和干净账户前置条件集中到收尾，用户明确质疑验证过重。主代理随后收窄工作，保留已定位的小范围 fixture 修复和真实生命周期问题，按变更影响复用原生、安装包及性能证据。

**采用的做法：** 全量回归绑定稳定候选；后续只对影响对应行为的输入变化补测。分别记录本次回归、已有故障、环境准备问题和范围外建议，每个失败保留具体依据。检查通过后，新增改动、失败或未解决疑点才触发更多验证。

启动路径改为延迟导入后，审查补齐原验收要求的三次采样：沿用同一个包，再补两次启动测量，未重做全部性能矩阵。干净账户验收后移是用户确认的范围调整，在记录中保持为 P6 待办。

## 4. 依赖与生成资源应在检查前准备好

**发生了什么：** 第四张票首次集成在干净工作树中因缺少 KaTeX 资源失败，旧工作区已有产物掩盖了前置条件。轻量验证随后接入 Web 资源准备，并加入对应检查。

终审第一轮又因缺少 TypeScript 失败。审查者创建顶层 `node_modules` 软链接后，Git 将其识别为未跟踪文件，触发固定候选的工作树漂移检查；项目的 `node_modules/` 忽略规则匹配目录。主代理核对依赖来源后改用普通目录，第二轮检查通过。第二轮仍曾先运行一次缺依赖检查，说明准备顺序需要落实。

**采用的做法：** 新工作树先按 lockfile 准备普通依赖目录和所需生成资源，确认工作树状态，再开始验证。审查简报明确允许生成已忽略的依赖、构建资源，同时保持受审源码固定。标准安装入口为 `npm ci`；复用依赖时核对 package 与 lockfile，并使用普通目录。

顶层 `node_modules` 软链接是可单独整理的项目环境陷阱。本次将其记录在复盘中；独立 pitfall 条目和工具规则调整仍为建议。

## 5. 跨票审查要覆盖完整消费者链

**发生了什么：** 第三张票的管理客户端改造影响了设置隔离、下载正文取消、nonce 和第二张票的首次草稿绑定。第五张票又发现 Dashboard Watch/Coordinator 的普通命令链仍继承宿主权限上下文。

**修复与经验：** 返修沿实际调用链检查共享客户端、所选后端、真实子进程和命令环境，关闭了消费者边界问题。后续修改凭据来源、传输层、恢复状态或共享接口时，从生产者逐项核对 CLI、后台进程、Web、桌面及委派消费者，并将合并后的共享模块变化交接给依赖票据。

继续维护现有组合回归和代码地图，复用已经覆盖这些边界的测试。

## 6. 归档保留原始证据，清理可再生副本

**发生了什么：** 验收过程产生了多阶段安装包、临时工作树、依赖、原生回执和性能采样。归档前逐项核对报告引用的临时路径，将仍只在临时目录中的浏览器运行状态等材料复制到证据目录，并保存保留映射。

**采用的做法：** 保留最终 DMG、历史包记录、失败输出、fixture、采样脚本及 26 个 agent 的转录；释放可再生的工作树、依赖和安装副本。归档大小按归档后实际材料统计，证据包含多个 DMG/ZIP 时按用途决定保留，避免仅按体积阈值删除。

仓库维护结论与经验，运行档案保存原始证据。两者通过运行标识、候选提交和证据索引关联。
