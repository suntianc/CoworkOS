# 开发交接与验证记录

本页落实 [P1、P2 与科学剪枝复盘](retrospectives.md) 中的交接经验。用于委派、返修、独立审查和归档；单人小改动按实际需要填写。具体命令以 [本地测试](testing-local-run.md) 为准。

## 派发与返修

把本轮增量、验证责任和可复用证据放在同一份交接中。可直接使用下表；路径填写本次运行的相对路径，凭据只记录来源和权限状态。

| 字段       | 需要交付的信息                                                                     |
| ---------- | ---------------------------------------------------------------------------------- |
| 候选与增量 | 起点提交、当前提交、工作树、允许改动的范围；返修填写前轮 finding ID 和本轮实际差异 |
| 消费者     | 从生产者到实际调用方的清单、受影响的接口和对应既有测试                             |
| 环境       | Node/Python 的解析路径和版本、锁文件、所选检查的依赖和生成资源；复用依赖注明来源   |
| 本轮验证   | 精确命令、目的、执行阶段与负责人；同一命令重复执行时注明次数及原因                 |
| 已有证据   | 候选、包 hash、检查命令、退出码、失败/跳过项、日志位置；说明本轮差异是否影响它     |
| 原生交接   | 持有 App/后端的负责人、当前实例、已完成步骤、唯一待补步骤、所需系统认证和回执路径  |
| 继续条件   | 下一步及检查点；执行者能继续的工作、主代理需接手的操作、确需用户完成的系统认证     |

确认新票据时核对验收命令的覆盖和次数：同一套测试覆盖多项行为可以共用一条验收；稳定性采样按明确次数执行。既有冻结验收按约定执行，返修简报分别列出本轮执行者增量检查和审查、集成、交付阶段的必需检查。文案变更默认使用文档/格式检查，并引用未受影响的包、原生和性能证据。

共享配置、鉴权、传输、下载或恢复接口变化时，沿 [代码地图](code-map.md) 核对 CLI、后台监控/子进程、Web、Electron 和委派消费者；下载同时检查网络文件与本地 `blob:`/`data:` 生成文件。删除能力时同步核对注册、设置入口、依赖、[发布测试计划](../scripts/release-test-plan.mjs)、runner 自测和中英文用户入口。共享模块集成后，将具体变化及组合回归交给依赖任务。

## 验证前准备

新工作树先按锁文件安装普通依赖目录、准备所选检查的生成资源，再记录候选和 Git 状态。审查允许生成已忽略的依赖与构建产物，受审源码保持固定。复用依赖时先核对 package 与 lockfile，目录形式见 [依赖软链接陷阱](pitfalls/testing.md#依赖软链接触发候选漂移)。

切换执行 CLI 时重新记录 Node/Python 的实际解析路径和版本。附件检查使用 [开发指南](development.md#准备环境) 中已准备的 Python 环境，先确认依赖导入，再运行所需测试。已提交差异使用明确的 `FORMAT_BASE`，见 [格式检查选择范围](pitfalls/testing.md#提交后格式检查没有选中文件)。

## 原生操作交接

由主代理或指定的一名操作者持有隔离 App 与后端。执行者交接现成候选、已完成证据和待补步骤；主代理接手后先核对当前实例、候选与回执，再继续尚未完成的步骤。原生启动与系统权限归属按 [开发指南](development.md#使用隔离的开发工作区) 操作。

“等待主代理操作”由主代理继续处理。需要用户系统认证时，准备好具体认证入口并说明原因，同时继续不依赖认证的工作。新通知先与当前状态对照，已经完成的检查直接引用回执。

## 输出、失败与复用

每次检查保存完整 stdout/stderr、退出码、源码提交、相关包身份及环境。查看另一段输出时读取原日志；诊断先运行最小失败场景，修复后运行受影响的验收。长任务按检查点记录新增证据、当前阻塞与下一步。

每个失败单独记录，使用下列分类，并链接相应日志：

| 分类           | 依据与后续动作                                     |
| -------------- | -------------------------------------------------- |
| 本次回归       | 失败行为与本轮差异相关，修复后保留原失败和通过回执 |
| 基线已有       | 同条件的基线对照；写明候选、环境和相同失败         |
| 环境或前置条件 | 具体缺失项，以及补齐后的同命令结果                 |
| 尚未确认       | 保留原始失败和最小待确认步骤                       |

复用证据时写明原候选和本轮影响分析。源码、环境或包内容发生相关变化时重验对应路径；验收约定的独立重复采样仍按次数执行。报告分别列出通过、失败、跳过和未执行项。

## 替换执行者与归档

更换 provider 时保留已有工作树、前轮发现、失败尝试和已接受证据，在交接中注明替换原因与实际返修次数。审计同时核对事件和前轮 verdict；工具的 retry 次数与返修计数分别报告。Workloop 计数语义及通用简报改进见 [工具建议](retrospectives.md#单列的-workloop-建议)。

归档前逐项核对报告引用：仍只在 scratch 的脚本、fixture、日志和回执移到保留目录，并写原路径到保留路径的映射。最终 CLI/App/DMG 记录提交、大小和 SHA-256；保留接受过的原生/性能/清理记录及失败尝试。已成功删除的合成 fixture 标记为预期缺失。按用途保留证据，释放可再生副本；核对无关工作树的 HEAD、状态与差异保持完整。
