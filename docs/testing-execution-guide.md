# CoworkOS 测试执行与发布规则

适用于当前本地多智能体 harness，以及后续 CLI、Mac App 和应用能力的持续更新。本文定义测试与发布机制；用例规划见 [能力与场景用例目录](testing-case-catalog.md)，新增用例格式见 [用例模板](testing-case-template.json)。已有本地 runner 的范围见 [本地验证](testing-local-run.md)；目录中的扩展门禁和指标仍需逐项落地，不表示已经执行。

执行决定：本套能力验收每次发版前在本地运行，不增加 GitHub Actions、PR 自动检查或定时任务。开发中按需要复现问题；发布时保留当前版本、最终包及本地结果。现有工作流不是这套验收的触发入口。

功能目录统一按基础、CLI、App、App 内应用、用户 case 五个环节组织，见 [主方案](testing-strategy.md)。本文仅说明这些测试的实现方式、执行环境和发布判定。单元、集成、E2E 和真实模型等标签属于执行属性。工程正确性、真实模型能力、安装包验收分别计分。一次更新是否可以发布，应由当前版本的行为断言、独立产物验收和平台证据共同决定。新功能同时增加能力声明、故障用例和验收器，才能自然进入后续回归。

## 1 当前基础与需要补齐的机制

`scripts/test.mjs` 自动发现 `test/` 下的 JavaScript、MJS 和 TypeScript 用例，编译后的 p0/p1/p2 保留原脚本断言；这些文件名与本文风险等级不同。本地 `npm run verify` 构建一次，执行静态、文档、源码卫生门槛、发布 runner 自测与确定性 Node 回归。`scripts/test-release.mjs` 按五环节复用已有 suite，浏览器、原生、真实模型和最终安装包分别验收。使用 `npm run check:source` 单独检查当前工作树的敏感信息和私有/生成目录；它不扫描 Git 历史。

| 已有基础                                    | 可以复用的部分                            | 需要补齐的机制                                  |
| ------------------------------------------- | ----------------------------------------- | ----------------------------------------------- |
| Node 内置测试、TypeScript、ESLint           | 单元、真实文件、HTTP、子进程和 Pi 集成    | 用例 ID、能力映射、结果归档、按环境识别跳过     |
| Playwright Chromium                         | 前端真实交互、竞态、流式显示、文档协作    | 与桌面宿主区别计分、稳定同步、分组与 trace 汇总 |
| `test/dashboard-fixture.mjs` 和本地模型服务 | 生产 Dashboard 与真实 Pi 的确定性协议验证 | 公共故障脚本、统一隔离、独立验收器              |
| `scripts/desktop-smoke.mjs`                 | 搬移安装包、原生引擎、退出和恢复          | 对最终 DMG 的同包验证、原生权限专用门禁         |
| CLI 编译、tgz 打包、onboarding 和 smoke     | 真实工具、配置、安装和多 Agent            | Linux 安装包矩阵、PTY、恢复身份与普通项目覆盖   |
| 故障夹具及行为回归                          | 缺陷复现和代表性任务契约                  | 当前版本基线、首跑成功率、结构化版本比较        |
| 本地构建与发布机                            | 复用现有 npm 命令，在各支持平台本地执行   | CLI 包测试、平台状态记录、能力覆盖与发布汇总    |

各支持平台分别记录本地结果：Mac 上的成功不能代替 Linux CLI 验收，Chromium 也不能代替 Mac 宿主。历史验收记录不能代替新版本验收。

## 2 测试范围与产品承诺

将能力分成共享核心、CLI 外壳、App 外壳和可选原生能力。共享核心覆盖 Task/Run、Main/Subagent、Inbox、队列、模型、恢复、文件、产出物、应用资源和权限。CLI 增加安装、参数、配置、TTY、信号和终端历史；App 增加 Electron、IPC、草稿、导航、工作台、连接、退出和升级。

平台基线沿用当前发布范围：CLI 为 macOS/Linux、Node 最低 22.19 与团队使用的 24 系列；App 为 Apple Silicon Mac。Computer Use 截图和控制要求 macOS 14+ 及对应权限。最终最低系统版本还需与 App 构建和发布文档统一。未承诺的 Windows CLI、Intel App、远程 Worker、多用户、自动更新等进入未来能力目录，不能混入当前支持列表。

| 测试环境         | 必须验证                                        | 不可替代的证据                     |
| ---------------- | ----------------------------------------------- | ---------------------------------- |
| Linux CLI        | 编译、安装后的命令、真实工具、恢复和非 Mac 降级 | Linux 上实际安装 tgz               |
| Mac CLI          | 同上，路径、权限、信号和可选依赖检测            | Mac 上实际安装 tgz                 |
| Web Chromium     | 共享 renderer、HTTP/SSE、编辑与交互             | 不能代替 Electron IPC 和原生窗口   |
| Mac App 自动环境 | 包内后端、renderer、加密设置、退出、数据恢复    | 签名和公证仍需最终发行包           |
| Mac 原生权限环境 | 真窗口观察、输入、人工接管、锁屏和撤权          | 解锁的专用机器及人工授权           |
| 干净用户环境     | 下载、安装、首次配置、首个任务、升级和卸载      | 无源码、无开发缓存的独立用户或机器 |

对 Office 附件读取等依赖，各测两种环境：依赖齐全时成功；依赖缺失时准确诊断、保留任务和数据。

## 3 测试实现方式与证据边界

| 层级              | 目的与真实边界                                     | 可以模拟                 | 执行频率               |
| ----------------- | -------------------------------------------------- | ------------------------ | ---------------------- |
| L0 静态与打包清单 | 编译、类型、依赖方向、格式、构建内容               | 无需模型                 | 发版前本地全量         |
| L1 单元与属性     | reducer、校验、状态机、预算、编码、错误映射        | 时钟、随机数、网络       | 发版前本地全量         |
| L2 契约与组件     | HTTP/SSE、工具 schema、Adapter、MCP、IPC、存储版本 | 外部模型、原生驱动       | 发版前本地全量         |
| L3 真实运行集成   | 生产 Pi、Coordinator、真实文件/子进程和持久化      | 模型协议服务             | 发版前本地全量         |
| L4 两端确定性 E2E | 用户从 CLI/App 完成操作，验证落盘结果              | 外部模型、部分原生对话框 | 发版前本地全量         |
| L5 安装包与原生   | 安装后的 tgz/最终 App、真实引擎、权限和迁移        | 普通模型可用协议服务     | 发版前本地安装包与人工 |
| L6 真实模型能力   | 模型自由规划、调用工具、完成任务和恢复             | 验收器不由被测模型控制   | 发版前本地固定任务集   |
| L7 长程与非功能   | 泄漏、负载、性能、长期 Watch、可用性和兼容         | 可控制的故障注入         | 发版前本地选定压力集   |

L3/L4 应真正经过生产 Pi 和执行工具，不能用假的 Agent 替掉执行链后声称验证了生命周期。L1/L2 验证一个协议正确，L6 验证模型是否能正确使用它；两类缺一不可。

前端 DOM 测试、Chromium E2E、Electron 宿主测试和 macOS 原生测试分别归档。Playwright 的 Electron 自动化属于实验性支持，可用于适合的宿主交互；保留现有原生 smoke 作为补充。系统文件选择与权限弹窗用独立人工/原生流程验收，模拟对话框只验证结果处理。[Playwright Electron 文档](https://playwright.dev/docs/api/class-electron)

## 4 核心不变量

不变量是异常和竞态下也必须成立的规则。围绕这些规则写断言，比只覆盖按钮或函数更能防回归。

| 不变量                                                  | 必须保留的证据                                   |
| ------------------------------------------------------- | ------------------------------------------------ |
| 一个会话恢复到原 Task，当前 Run 的终态只由当前 Run 裁决 | session/Task/Run 映射、activeRunId、当前进程事件 |
| 同 Task 的启动和停止按约定串行，旧进程不能覆盖新 Run    | 启停屏障、子进程数、状态事件                     |
| Task completed 不能掩盖未结束委派、问答或执行失败       | 队列、Inbox、人工问题、完成前置条件              |
| 消息、回调和事件重投递不产生重复可见效果                | 事件身份、ack、marker 或操作 ID 的实际次数       |
| 资源更新通过 revision CAS，冲突保留草稿及候选           | 修改前后 revision、原始字节和候选文件            |
| 导出、预览、比较和未接纳的候选不修改源资源              | 源资源 hash/revision、导出字节                   |
| 发送、附件读取、语音和迟到响应只属于捕获的会话          | Task ID、草稿 token、导航 token、附件版本        |
| Stop/退出能回收应回收的进程并落盘                       | PID/进程组、日志尾部、恢复后状态                 |
| jobs 按授权可独立存活，取消不能遗留子进程               | job 状态、父子 PID、监督归属                     |
| 模型不能自行授予、扩大或恢复 GUI 权限                   | 宿主授权、Task/窗口/模式/到期时间、动作审计      |
| API Key 不进入 renderer、共享日志和发行包               | 合成 canary 密钥扫描、IPC 响应、包清单           |
| 更新失败不会破坏旧数据；未来数据版本不被静默降级        | 备份、版本标记、迁移前后数据摘要                 |

“不重复执行”需要明确边界：拥有 operation ID、持久结果或可验证产物的操作可以去重；任意 shell 命令在副作用发生后、结果落盘前崩溃，通常无法保证 exactly-once。测试必须确认这种不确定状态被保留并要求核对，不能自动重放未知副作用后仍报告保证一次执行。

## 5 能力目录与覆盖判定

能力使用稳定 ID，例如 `runtime.resume`、`coordination.delegate`、`resource.cas`、`cli.onboarding`、`desktop.quit`。同一能力关联多个测试，一个测试也可覆盖多个能力。目录至少保存以下字段：

| 字段                               | 含义                                   |
| ---------------------------------- | -------------------------------------- |
| `id`、`owner`、`risk`              | 稳定身份、维护者、P0/P1/P2             |
| `status`、`introducedIn`           | 当前能力或未来规划，首次版本           |
| `entrypoints`、`platforms`         | CLI/App/API 及支持平台                 |
| `implementationPaths`、`consumers` | 变更影响路径与接口两端                 |
| `requires`、`permissionMode`       | 原生引擎、视觉模型、系统授权等前置条件 |
| `invariants`、`requiredLayers`     | 不变量及必须提供的证据层               |
| `caseIds`、`requiredProfiles`      | 关联 case 及每个环境的必跑范围         |
| `docs`、`compatibility`            | 产品承诺、兼容和迁移规则               |

能力覆盖状态只允许 `planned`、`implemented_unverified`、`verified`、`regressed`、`not_applicable`。只有当前构建在该能力要求的全部环境中运行并通过，才记为 verified。测试文件存在、历史通过、在不适用平台跳过，都不能把能力标成 verified。

P0 为数据损坏、越权、凭据泄露和主链路失效；P1 为重要能力不可用、恢复错误、持续交互缺陷；P2 为次要兼容与体验退化。优先级与测试层级独立，不能把“单元测试”当作低风险。

覆盖面板以“能力 × 入口 × 环境 × 证据层”为单位，显示应跑、已跑、失败、跳过及过期证据。代码行/分支覆盖率是辅助指标；可从核心模块分支覆盖 80% 的建议目标起步，先做现状测量再设门禁，不把全仓平均值当作发布标准。状态转移、错误分类、CAS/权限拒绝与崩溃点覆盖比总行数更重要。

## 6 用例标准与验收器

每个 case 必须能回答：测哪个能力、从哪个入口、什么初始状态、如何触发、什么结果算成功、失败后如何定位。模板保留一个业务场景及多个执行变体，避免把本地模型 fixture 和真实模型混成一个结果。

必填项为稳定 ID、维护者、风险、能力、输入 fixture、前置条件、步骤、独立断言、预算、清理、实现入口和证据。无法自动化的步骤注明人工角色和所需收据。待实现 case 的 `implementation` 为 null，报告不能把它计入执行通过数。

验收器由测试侧执行，fixture 和标准答案保存在 Agent 无权修改的位置。评估器最好运行在独立进程或只读目录。被测 Agent 修改程序时，需要核对测试文件 hash；它自行运行“测试通过”并不算独立验收。

| 任务产物     | 结构和语义验收                                  | 不合适的单一判定               |
| ------------ | ----------------------------------------------- | ------------------------------ |
| 代码         | 隐藏行为测试、允许变更路径、测试 hash、实际运行 | 回复称已完成、精确匹配代码文本 |
| CSV/报告     | 独立解析、数值、行数、排序、缺失值规则          | 模型打分或只看文件存在         |
| TXT/Markdown | UTF-8、必要段落/引用、资源 revision 和保存内容  | 比较随机措辞全文               |
| PDF/DOCX     | 可打开、页数/元素、内容、渲染检查、无明显遮挡   | 文件后缀或文件大小             |
| GUI          | 输入后目标控件状态、保存后文件重读、动作权限    | “事件已发送”或截图生成         |

视觉与可访问性验收同时使用几何断言和人工抽样：窄窗口不横向溢出、输入不遮最后回复、焦点可达、减少动画生效。像素快照固定字体、系统、viewport 和动画时间，升级 Electron 或字体后复核基线，不能一键接受全部图片变化。

## 7 统一 fixture 与故障注入

建立 `tests/support/` 下的隔离环境、脚本化模型服务、协议收据、进程监督、虚拟时钟和验收器。先包装已有 fixture，逐步复用；现有 `test/` 与 `e2e/` 不必立即迁移。

模型 fixture 按请求内容和工具结果选择下一步，校验工具名、schema、图像块、参数及上下文。固定回复按请求次数推进只适合简单协议测试，关键集成应检查请求前置条件，否则错误执行顺序也可能得到假通过。单元层使用假时钟；真实 Pi/子进程层保留真实计时和配置好的有界预算。

| 故障面     | 必测注入                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------- |
| 模型与网络 | 401/403、结构化 model_not_found、429、502/503、DNS/TLS/连接错误、首字节超时、半流断开、畸形工具参数 |
| 流式编码   | 每字节切分 UTF-8、工具参数跨块、无换行尾部、重复/延迟事件、文本与思考交错                           |
| 进程       | spawn 失败、非零退出、SIGTERM/SIGKILL、孙进程、stderr 大输出、后端中途崩溃                          |
| 持久化     | EACCES、ENOSPC、写入/rename 失败、日志尾部损坏、旧/未来版本、锁过期                                 |
| 并发       | 双启动、取消与完成、两个写者、A→B 导航后 A 回包、草稿/附件边读边改                                  |
| 原生       | 引擎缺失、超时、取消、预览迟到、锁屏、系统授权撤回、目标窗口变更                                    |

故障注入点要落在因果边界：副作用前、成功后但收据前、事件已落盘但 ack 前、候选完成但 CAS 前、迁移已备份但版本标记前。每个点都检查原数据、当前状态、恢复入口与剩余进程。

竞态用屏障、手动释放 Promise 或 fixture 状态协调；不靠增加 sleep“修复”。随机 interleaving 保留 seed 和最短失败序列。属性测试优先覆盖状态转换合法性、CAS 单赢家、Inbox 投递/ack、scheduler 租约和序列化 round-trip；可先用 Node 写 seed 固定的生成器，不为形式统一强制引入新框架。

## 8 测试环境隔离与调度

每次运行分配唯一 root，包含 project、user-data、workspace、global-index、tabs-index、pi、outputs。用 allowlist 构造环境，移除宿主 `COWORK_*`、`PI_*`、`ATRIA_HOME` 及代理/模型覆盖；有意继承的字段单独记录。

CLI fixture 设置独立 `ATRIA_HOME`、`COWORK_CONFIG`、`COWORK_WORKSPACE`、`PI_CODING_AGENT_DIR`；Dashboard 同时隔离 `COWORK_GLOBAL_INDEX` 和 `COWORK_TABS_INDEX`；桌面使用 `COWORK_DESKTOP_DATA`。用户 HOME 仅由专用干净用户环境管理，测试脚本不覆盖真实用户数据。路径配置、默认路径测试和显式覆盖测试分别安排，避免一直指定显式配置而漏掉用户默认行为。

端口由后端绑定 0 并报告实际地址；现有“先探测空闲端口再启动”的方式存在抢占窗口，应逐步改进。所有子进程注册到测试监督器，after/finally 回收进程组、关闭服务和验证零遗留。

不同资源类使用调度标签：普通单元可并行；真实 GUI 与权限用 `exclusive-desktop` 串行；安装/升级用隔离 profile；长程任务独立机执行。缓存预热计入准备阶段，冷启动测量使用独立缓存。不要让预热结果覆盖冷启动失败记录。

每个测试设置总体 deadline、单步 deadline、模型调用/Token/费用上限和清理 deadline。真实模型测试默认禁用外网工具，确需网络的 case 指定允许目标。工程套件通过网络策略仅允许本地 fixture，避免误用真实密钥或产生费用。

## 9 CLI 与 App 共享 case 的执行方式

定义测试侧入口适配器，提供 createTask、send、waitForState、stop、resume、readArtifact、collectEvidence。它负责驱动产品，不实现产品业务。CLI 通过安装后的命令与 PTY；App 通过用户可见控件与可信宿主操作；API 入口保留给集成层。

共享 case 使用相同输入与独立 oracle，比较归一化语义：Task 身份、资源内容、revision、产出物、终态、副作用次数、权限边界。忽略时间戳、随机 ID 和展示措辞。不能强求 CLI/App 的目录和配置文件一致，因为两端现在独立存储。

至少 8 个核心任务在两端各自执行：文件创建、代码修复、数据报告、双子智能体、人工问答、取消继续、模型失败继续、产出物发布下载。恢复测试必须退出并启动新进程，不仅调用同进程 resume 方法。App 文件编辑和原生权限增加专属 case；CLI 配置、TTY 和历史选择增加专属 case。

没有 GUI 宿主的 CLI 对 Computer Use 应给出能力不可用说明，不能伪装完成。

## 10 真实模型能力评测

真实模型使用固定版本的数据集、任务说明、独立 oracle 和允许工具范围；模型自由选择操作顺序。脚本化 fixture 的路径确定性不能替代模型规划能力。模型兼容测试分别覆盖文本+工具、推理参数、视觉、Main/Subagent 和压缩/恢复；声明不支持的能力测明确降级。

首版建议核心 8 个任务在 CLI/App 各重复 3 次，另测应用与原生专项；这只是建立基线的样本量，不足以证明稳定 95% 成功率。后续对高价值类别累计 20–30 次独立运行并给出区间估计。稳定集、扩展集和暂不公开的挑战集分开，冻结后不能按某版失败随意删题。

| 指标                 | 定义与用途                                               |
| -------------------- | -------------------------------------------------------- |
| 端到端首跑成功率     | 首次完整任务独立验收成功数 / 全部尝试；包含真实网关故障  |
| 服务可用条件下成功率 | 另列分类明确的 provider/环境失败；保留完整分母与排除规则 |
| 自动恢复率           | 注入允许重试的错误后，在原预算内成功的比例               |
| 人工协助后成功率     | 明确记录协助内容、次数和额外调用，独立于首跑             |
| 误报完成率           | Task/回答声称完成但 oracle 失败的比例，核心集目标为 0    |
| 副作用重复率         | 不该重复的操作实际执行超过允许次数的比例                 |
| 耗时与成本           | 首个可见反馈、首次有效工具、总完成、恢复耗时、Token/费用 |
| 可恢复与可诊断率     | 失败有正确状态、保留证据、有效继续入口的比例             |

比较上一发行版和候选版时固定模型/网关/参数、任务集、工具和预算，交错执行相同任务。报告每项配对变化及失败归因，样本允许时用配对统计/重采样给区间。建议把下降 5 个百分点作为调查触发值，而非小样本自动统计门禁；P0 数据/越权问题和确定性主链路失败立即阻断。

首版候选发布的最小真实能力门槛：8 个基础任务各在两端重复 3 次，共 48 次；CASE-17 至 CASE-21 的 5 个交互任务同样执行，共 30 次。两个集合分别报告首跑成功率并达到至少 90%，两个入口每个任务均至少 2/3 成功，零误报完成、越权或破坏数据。它是建议的初始验收规则，不是现有能力成绩或可靠性保证。若失败明确来自外部服务，可在保持原记录的前提下做额外确认；不能把重跑成功替换第一次失败。

开放型研究/Office 输出先看结构与事实核验，再按预先定义的人工 rubric 评分。LLM judge 可作辅助，保留 rubric、judge 版本与原始意见；不能作唯一成功判据。

## 11 发版前本地执行流程

每次候选发布手动启动一次本地验收，按五个功能环节看结果。完整自动化与包体验的耗时分别记录；真实 GUI 串行运行，避免与日常桌面操作互相干扰。没有要求每个 PR 执行这套能力集。

| 本地批次        | 检查范围                                          | 当前执行入口                                               |
| --------------- | ------------------------------------------------- | ---------------------------------------------------------- |
| 准备            | 记录源码状态、版本、配置与依赖；建立隔离用户/项目 | 人工记录；准备 Linux CLI 与 Mac 环境                       |
| 一 基础功能     | 单元、契约、进程、模型/队列/恢复及静态检查        | npm test；npm run check                                    |
| 二 CLI 专门功能 | tgz 安装、首次配置、TTY、信号、继续会话           | npm run cli:pack；安装到独立 prefix；按目录操作            |
| 三 App 功能     | renderer 回归、最终包宿主、草稿/退出/升级         | npm run test:browser；npm run desktop:dist；最终包人工操作 |
| 四 App 内应用   | TXT 和真实窗口操作                                | 按应用本地验收手册；真实引擎和解锁 Mac                     |
| 五 用户 case    | 固定用户任务、交互、恢复和最终交付                | 当前模型/任务入口；确定性与真实模型分开记录                |
| 汇总            | 当前构建结果、失败、阻塞、体验问题和产物 hash     | 保存一份本地发布报告，不依赖 GitHub 状态                   |

上述命令运行的是已有 suite，并不能发现所有尚未实现的目录用例。应用逐步操作和新增边界手动记录为 PASS/FAIL/BLOCKED/NOT_IMPLEMENTED/NOT_APPLICABLE。Linux/Mac 与 Node 版本由本地对应机器或虚拟机收齐，缺少支持平台证据保留为未完成。修复后复测失败项及相关边界；若最终包发生变化，重做受影响的包验收并记录新 hash。

本地 runner 已接入：`npm run test:release`，操作见 [本地执行说明](testing-local-run.md)。默认构建一次、按五个环节运行现有 suite，保存每步日志、测试统计、源码摘要及待验清单；真实 Electron/GUI 用 `--native`，包构建用 `--packages`。它没有实现整个规划目录，具体用例仅部分映射；真实模型、最终安装及手册体验仍须另验。现有 npm run test:desktop 是打包目录 smoke，不能替代最终 DMG 验收。

发布硬门禁：P0/P1 必跑 case 零失败；关键数据/权限/恢复分支不能跳过；所有宣称支持的平台有当前构建证据；新增已交付能力有测试映射；迁移与失败恢复通过；包内容无凭据及用户数据；最终发行物身份可追溯；公开 Mac 包通过签名、公证、staple/Gatekeeper 和干净安装；真实模型核心集达约定门槛。

跳过使用三种分类：平台不适用、依赖/权限缺失、临时隔离。平台不适用由支持矩阵批准；必跑环境依赖/权限缺失记为 BLOCKED，不能标 PASS；临时隔离保留 owner、issue 和截止日期，不得绕过 P0 发布门禁。测试框架的 skip 结果必须被汇总器重新解释。

确定性门禁以第一次执行为准。重跑用于诊断，记录 `pass_after_retry`；P0 不允许用重跑转绿，其他 flaky case 必须修复或按受控隔离流程处理。真实模型的计划重复运行属于采样，不能称为测试重试。

## 12 冻结发行物与升级验收

CLI 和 App 分别冻结最终文件及 SHA-256、源码 commit、dirty 状态、依赖锁摘要、构建环境和能力版本。正式发布使用已审核干净源码；开发工作区验证可记录 dirty 并保留源文件清单，但不能冒充可复现正式构建。

CLI 从 tgz 安装到临时 npm prefix，移开源码入口并使用独立生产依赖。在无 Electron、Swift 和开发 Python 环境中验证基础链路；可选原生场景另配依赖。测试必须调用 prefix 下的 atria，不能 fallback 到仓库 dist。

App 应测试最终 DMG 中解包的 App，再以同一 hash 分发；不能先测 `--dir` 的开发包、之后重建 DMG 就沿用旧结果。签名或公证后的字节变化需要记录最终身份。安装路径含空格/Unicode、只读安装目录、从 Applications 启动、Finder 双击和非终端 PATH 分别覆盖。

升级用上一正式版及必要的旧数据格式制作 fixture：会话、草稿、附件、资源、历史、绑定、模型设置、人工问答和活跃/等待任务。新版本读取后验证身份与内容；迁移中故障必须保留可恢复备份。降级到不支持的数据格式应明确拒绝，不静默改写。CLI/App 的独立配置不得互相覆盖。

当前采用手动升级，应测试替换 tgz/App 和数据保留。未来引入自动更新，再增加下载中断、校验/签名失败、安装失败回滚和渠道切换，不把未实现更新器当作当前测试目标。

## 13 性能和长程基线

先采集上一版基线，再定 SLA。性能运行固定机器、资源和模型 fixture，冷/热启动分开记录；真实模型网络延迟另列。

| 指标                   | 建议起始场景与门槛                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| CLI/App 启动与列表加载 | 0/100/1000 Task；中位数与 p95 较基线退化超过 20% 且超过绝对容忍值时调查                                            |
| UI 流式负载            | 10 分钟流、1 MiB 输出、分块/高频 delta；无输入阻塞、消息丢失或布局覆盖                                             |
| Stop                   | 点击后立即呈现 stopping；进程组在配置 deadline 内退出，无剩余可取消作业                                            |
| 内存/文件描述符        | 100 次创建/取消/恢复/开关文档后趋于稳定，无单调增长                                                                |
| 大资源                 | 文本/附件/对象数在预算以内成功，预算边界和超限安全失败                                                             |
| 后台长程               | 普通发版本地短程检查唤醒/去重/重启；长程机制变化按需补 2–24 小时，主要长程版本另选 72 小时专项，不要求后台定时执行 |

起始负载和 20% 阈值是待校准目标。发布比较至少重复 5 次；实际 UI 采样需记录硬件及负载。长期 Watch 测日界线、系统睡眠、时区/时钟变化、断网恢复、重复事件及服务重启。不是所有 Task 都需要运行 72 小时。

安全检查围绕实际产品边界：Host/Origin/session token、可信 IPC、路径/符号链接、保护路径、资源权限、第三方工具声明和候选接纳。另测试不可信文档/工具结果诱导越权；技术执行端必须拒绝无授权行为。现有 Task capabilities/GrantedPermissions 不是统一 OS 沙箱，验收和对外描述都不得扩大承诺。

## 14 结果报告和证据保存

每次执行生成 run manifest，记录构建/包 hash、case/dataset 版本、系统、入口、依赖、模型/参数、预算、seed、开始结束时间和前置条件。每个 case 记录首跑状态、失败分类、断言、重试、证据路径及实际费用；模型未知错误归为 unknown，不按文案猜网关根因。

报告分开显示工程回归、原生/发行包、真实模型、性能和人工验收，并给出发布 PASS/BLOCKED/FAIL。以下任一缺失都不能出“全面通过”：必跑 case 未实现、必跑平台没跑、原生条件不足、证据来自旧 hash、核心数据断言未执行。

失败保留脱敏 stdout/stderr、最后持久状态、HTTP/事件序列、进程清单、实际产物和 oracle 差异；浏览器增加截图/trace。Playwright trace 能帮助检查动作、DOM 和网络，适合作为交互失败收据。[Trace Viewer 文档](https://playwright.dev/docs/trace-viewer)

发布报告本地保存测试合成数据和脱敏摘要。真实模型任务使用专用凭据和无私人内容 fixture；原始对话与 trace 默认本地保留，分享前扫描 canary 密钥并做字段和正文脱敏。失败证据与候选发布摘要至少保留到下两个发行版；无需自动上传。

## 15 新功能和缺陷修复的完成标准

每项新功能执行同一个流程：

1. 增加能力 ID、产品承诺、平台/权限和负责模块；变更共享接口时列出生产者与消费者。
2. 描述正常完成、失败/拒绝、取消/恢复、并发或重复输入四类行为；不相关维度明确说明理由。
3. 选择必须测试层，增加独立 oracle 和 fixture。共享能力至少覆盖一个 CLI 与一个 App 入口，宿主专属能力测明确降级。
4. 持久格式变化增加上一版升级、失败不破坏数据、未来版本拒绝用例；模型工具变化补真实 Pi contract 和真实模型小集。
5. 将 case ID 关联能力、本地发布批次、执行方法和 owner；生成报告确认真的被发现并执行。
6. 更新用户/API 文档、兼容策略和发布条目；评审行为断言，避免只验证函数自己返回的值。

修复 Bug 时，先把最小复现加入目录并保存修复前失败证据，再修产品并验证同一个断言通过。涉及系统性缺陷时再加入相邻变体，例如“晚返回清空草稿”应同时验证附件、语音、重试和切换会话。旧问题已经进入稳定集后，不依赖人工每版重新回忆。

新 Adapter 建立可复用契约套件：发现/创建、读取/查询、校验/编辑、CAS/历史/撤销、导入导出、取消/预算、Main 首轮工具发现、后续刷新、Subagent read/candidate、UI 草稿与跨会话。每个插件用同一套基本合同再加领域验收，不在主测试框架复制软件分支。

## 16 落地顺序与工作量

按交付批次组织，而非一次重写所有测试。

| 批次             | 交付物                                                               | 验收                                              |
| ---------------- | -------------------------------------------------------------------- | ------------------------------------------------- |
| A 发布前必需     | 能力表、现有用例映射、环境隔离、CLI 高风险回归、跳过汇总、最终包收据 | 恢复身份/配置问题有明确结论；全部 P0 必跑项可追踪 |
| B 统一确定性回归 | fixture、故障模型服务、case 注册、CLI/App 8 个共享任务、报告         | 从一次命令获得完整能力 × 平台状态                 |
| C 发布能力评测   | 独立 oracle、真实模型任务集、基线对比、费用/样本记录                 | 相同任务比较上一版与候选版，所有失败保留          |
| D 后续扩展       | 本地原生、soak、属性测试、性能、挑战集、影响选择                     | 随发布或按需运行，新能力能按模板接入              |

以一名熟悉仓库的工程师计，A 可按 3–5 个工作日、B 按 1–2 周、C 按 1 周、D 逐步实施估算；这是计划估算，先用现有套件执行时间和原生机器条件校准。签名凭据、干净 Mac 和系统权限需要独立准备，不能用增加测试代码替代。

第一批应优先完成 `CLI-03`、`CLI-04`、`RUN-03`、`RUN-04`、`COORD-03`、`RESOURCE-02`、`COMPOSER-02`、`DESKTOP-03`、`SEC-01` 和发行包核心验收，再扩展模型任务质量与长期负载。完整用例及验收要求见 [用例目录](testing-case-catalog.md)。

## 17 重点用例的执行步骤

### CLI 恢复原 Task

准备独立用户目录和项目，使用 fixture 驱动 Main 写入 memory、投递未消费 Inbox 并启动可暂停的委派。用普通 atria 启动，不预设 `COWORK_TASK_ID`。记录 Pi session ID、Task ID、Run、memory hash、Inbox ID 和委派 ID；正常退出后运行 `coworkos --continue`。要求 session/Task 身份不变，原 Inbox/委派可继续，memory 完整，未产生额外 Task。再创建第二会话并切回第一会话，确认选择身份正确。当前已知问题应先得到可重复的红色结果；修复后同一断言必须转绿。

### 普通业务配置保护

先在隔离用户目录 init，再创建 `project/config.json`，内容为 `{"projectName":"ordinary-project"}`。保存原 hash，分别运行 doctor、普通启动、init 和 init --force；所有操作不得修改业务文件。另创建 `.cowork/config.json`、指定 `COWORK_CONFIG` 和环境变量，按确定的产品契约核对实际请求，不从配置解析返回值推断。源码根目录兼容单独测试，不能因此让所有外部项目接受根配置碰撞。

### 工具成功后流中断

fixture 首轮要求 bash 追加 marker，下一轮在部分文本后切断 SSE。独立核验 marker 次数为 1、Task.failed/waiting 符合契约、部分文本和工具证据保留。App 输入一份带附件的后续草稿后点击恢复；CLI 退出再继续。要求恢复请求使用原会话，不消费新草稿，不复制原附件，marker 不重复，最后文件通过 oracle。再增加“副作用后收据前强杀”变体，要求产品暴露不确定状态，而不是假定能安全自动重放。

### 双写者资源冲突

准备 revision r 的资源。两个生产接口读取 r，用屏障使它们同时提交不同内容；要求一个成功、另一个 revision_conflict，最终内容是合法赢家之一，history 只有真实提交。App 失败者本地草稿不丢。再让人工先提交 r+1，Subagent 接纳 r 的候选；要求拒绝、候选仍在、源 hash 不变。重读再生成候选才允许提交，不能修改旧 baseRevision 绕过测试。

### 保存失败不能关闭 App

独立 profile 中输入 Composer 草稿、问答草稿和编辑器修改，阻断目标原子写入。通过真实退出路径触发保存；要求窗口保留、错误可见、后端未误停、所有最新草稿仍在。解除故障后再次退出，在新随机端口重新启动，独立读取数据和 UI 核验。另在保存等待期间输入新文字，确认收据对应最新版本。

### 最终包与升级

冻结上一版数据及最终 CLI tgz/DMG SHA。Mac 从 DMG 解包安装，在独立用户下配置并运行文件任务、TXT 关键流程、正常退出和重启；CLI 安装到独立 prefix 做同等基础任务。用上一版 fixture 升级，核验 session/Task、草稿、资源、历史和加密连接摘要；迁移中写失败时检查备份和版本标记。收据中的最终包 hash 必须等于待发布文件，不用开发包 smoke 结论替代。

## 18 用例拆分与维护规则

每行 case 的实现需要具体测试名称/路径、前置条件和 oracle；先审现有测试再填写映射，不按文件名直接标已覆盖。每个输入变体给子 ID，如 `MODEL-03/503/main`、`RESOURCE-02/two-writers/app`，报告同时保留父能力和实际子项数量。

新增能力可引用既有 case，但若改变协议/数据/权限必须增加针对变化的断言。每个修复新增最小复现，核心稳定集保留它；删除 case 需要说明产品能力被删除、被哪项替代及对应文档变更。不存在“测试数量增加就覆盖全面”的验收标准。

## 19 人类交互的执行时机与断言

主目录仍为五个环节。人类交互测试归基础协议、CLI 入口、App 交互/显示、应用协作及用户任务，不增加第六个功能环节。

### 区分用户动作

补充资料、修改要求、显式停止、停止后继续、完成后的下一轮和回答人工问题，各有独立身份和预期效果。输入框编辑不是提交；文本“请停止”是否由模型理解与点击 Stop 的技术取消分别验收。队列/steering 接收不保证能立刻打断当前工具。

### 使用阶段屏障控制用户操作

核心场景在等待模型首字节、文本流中、工具执行中、委派等待、人工问题待答、重试退避、终态提交前后这些时机触发适用操作。基础和入口测试用脚本化模型与真实可阻塞工具建立屏障，确认阶段后再模拟用户动作，不依赖固定 sleep 猜时机。

先用一张映射记录支持的操作 × 阶段。插入、Stop、回答不是在所有阶段都具有同一种语义：已完成后发送是新一轮，待答时普通补充不是回答，stopping 时新指令须按公开契约排队或拒绝。基础层覆盖共享状态转换；CLI/App 对正常流程和高风险边界分别执行；真实模型集抽代表时机检验实际更新目标。

### 分别核对接收和生效

每项收据至少包含原 Task/Run、用户输入身份及序列、接收返回、持久事件、实际下一次模型请求或消费证明、工具副作用、最终产物和界面快照。202/accepted 只证明接收的对应阶段；不能直接认定要求已进入模型上下文。生效点之后的新操作使用更新要求，生效点之前已执行的操作保留真实记录。

回包丢失场景保留“不确定提交”，独立读取服务端记录核对；若缺幂等协议/恢复机制则记能力缺口，不能用测试夹具替产品实现去重。连续相同文本使用不同合法消息身份，历史不能按文本去重。

### 多轮显示的验收

至少建立 5 轮正常轨迹和一条正常/取消/继续/失败/恢复混合轨迹。独立事件清单对照每轮用户文本、助手结果、思考、工具 ID、stdout/stderr、终态和耗时归属；同时核对历史数量、合法重复内容、当前忙碌状态、草稿和产物链接。滚到底部、向上阅读、展开工具、选中文字、窄窗口和输入变高分别检查可见结果。

刷新和新进程重启后重建同一轨迹，检验持久记录与界面一致。CLI 用 PTY 输出和实际状态；App 用生产 renderer/实际 Dashboard，必要时录制 trace。真实模型 case 同时跑独立产物 oracle，不能只做截图断言或只验证最后产物。

### 确定性时序回归

下面时序是持续补齐的回归设计；按当前用例实际断言确认覆盖。CASE-22 至 CASE-24 不自动进入真实模型费用批次。

| 边界            | 最少时序变体                                                                 | 同时核对                                                               |
| --------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 接收与确认      | 事件先于 HTTP 响应；响应先于事件；服务端接受后响应丢失；重连快照先于迟到响应 | 同次提交身份、用户消息数量、实际消费与副作用、新草稿                   |
| 同 Task 换 Run  | 针对 A 的请求在 A 活动时处理；A 结束后处理；B 已启动后处理                   | 预期执行身份、服务端拒绝或显式重新选定行为、B 的队列及工具无误操作     |
| 工具/压缩和补充 | 两条修正已接受后释放工具；压缩中接受输入后释放；保存失败/消费前退出          | 请求中真实工具结果、指令顺序、保存承诺、恢复消费记录                   |
| 历史重建        | 先重建 in-progress 项再完成；完成事件先到再旧快照；断连后旧 Run 事件迟到     | 各 Run/tool-call 终态、显示次数、当前状态不倒退、原进程/job 不重复启动 |
| 人工问题/权限   | 待答时停止；目标改变后旧答案到达；已解决后重新加载；问题弹窗中组合输入       | request/Task/Run 身份、失效状态、未发送草稿、失效授权后无动作          |

实现用门闩、受控响应代理或事件释放顺序，在生产入口制造时序。不要让 fixture 改写生产身份校验、替产品自动补发或去重。跨平台终端用实际 PTY 字节与窗口尺寸事件；浏览器操作通过可见控件；Mac 窗口授权和宿主退出保留原生验收。
